## 5. 建议

### 建议一：阶段四改 `agent_admin_front`，绝不在 `agent_front` 里开 `/admin/*`

理由：两套工程是**刻意隔离**的——token 键不同（`admin_token` vs `token`）、响应外壳不同（`code:200` vs `code:0`）、API 前缀不同（`/api/admin` vs `/api/v1`）、端口不同、鉴权体系不同（`admin` 表 vs 用户表）。在 `agent_front` 里加管理端路由，等于把两套契约混进一个 SPA，是明确的架构倒退。

> 如果阶段四任务书是按「`agent_front` 里有没有 admin 目录 / `/admin/*` 路由」来写的，那**任务书的前提假设有误**——建议在阶段四开头先纠正这一点，否则会产出一份「同工程内塞管理端」的错误方案。本次调研已经把答案备好（第 1 节）。

### 建议二：范围收敛为「最小可用 3 页 + 1 api」

因为后端零改动、框架现成、审核与结算是**闭环必需的人工操作**（没有审核，商家进不了工作台；没有结算，商家拿不到钱）。先把这三件事打通，其余（总览卡、详情页、导出）留到有真实诉求再加。

### 建议三：把这三个坑写进阶段四任务书，可省一轮返工

1. **登录态键名是 `admin_token` / `admin_info`**（不是 `token` / `user`），照抄主前端的键名会导致「静默 401 跳登录」
2. **`POST /merchant/settle` 是不可逆写操作**（写 `merchant_settlement` 并锁定批次）：前端必须二次确认 + 明确展示「本次将结算 **N 单 / ¥X**」，并对无待结算的商家禁用按钮。这个接口比审核更需要防护——审核可改回，结算不能
3. **角色权限要落到按钮级**：`settle` 是 `write_roles`（role 1、2），**role 3 审核员只读**；菜单/路由已按 `meta.roles` 过滤，但结算按钮还需单独判 `store.role !== 3`，否则会出现「页面进得去、按钮点了 403」

### 建议四：验收时优先测「审核」这条链路

它是唯一能让阶段三成果真正可用的开关：未入驻账号申请 → 管理端看到 `pending` → 拒绝（填原因）→ 用户侧看到 `audit_reason` → 重提 → 通过 → 商家能进工作台。这条链路阶段三 e2e 已用脚本验证过 23 项，阶段四只需把它搬到界面上再走一遍。
