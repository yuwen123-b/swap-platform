## 3. 真实 HTTP + 真实库端到端（51 项，全绿）

用 uvicorn 起独立服务（不复用可能过期的常驻进程），覆盖前端所依赖的**每一个字段与分支**：

| 分组 | 关键断言 |
|---|---|
| 商家列表 | 免登录 200 + `code=0`；`total=5`；8 个字段齐备；**确认无 `distance`**；`logo_url` 全 null（故 emoji 占位是必须的）；`product_count` 为整数 |
| 分类筛选 | `?category=打印` 精确命中 1 家；不存在的类型 `total=0`（走「该类型暂无商家」空态） |
| 店铺商品 | 返回 `{ merchant, list }` 形态；商品 id 升序 [1,2]；字段齐备；`image_url` 为 null；404「商家不存在或暂未开放」 |
| 兑换 | 未登录 401；兑换成功 `code=0`；核销码为 6 位数字**字符串**；`points_balance=111`；`expires_at ≈ 30 天后`（实测 29 天 23 小时）|
| 落库 | `user.points` 扣为 111；`points_log` 有 `source=5, points=-50, related_id=订单id`；商品 `stock-1 / sold_count+1`；单据状态=1 |
| 我的兑换 | 分页字段齐备；`status=1/2/3` 过滤各自生效；行内含码/商家名/过期时间 |
| 免费券 | `points_cost=0` 时 `points_balance` 为 **null**（前端据此走「余额不变」分支）；不产生流水；仍生成核销码；积分不被扣 |
| 错误分支 | 积分不足 → 400「积分不足：本次兑换需要 50 积分，你当前有 0 积分」；商品不存在 → 404；库存 0 → 400「库存不足」（前端据此显示「已兑完」） |

## 6. 与《变更影响分析》的两处实现级调整（更优解）

| 项 | 分析稿 | 实际实现 | 理由 |
|---|---|---|---|
| 兑换成功后的编排 | `RedeemConfirmDialog` 内部持有 `result` 并切换到核销码视图 | 弹窗只负责「确认」，成功后 `emit('success')`，由父页面拉起 `RedeemCodeDialog` | 核销码弹窗要独立出现在「我的兑换」页；合并后那一页就得传个假 `product` 进来（为复用而耦合）。父页面本来就要刷新余额/库存，由它编排最自然 |
| `rs-*` 类名 | `rs-1/rs-2/rs-3`（数字） | `rs-pending/rs-redeemed/rs-expired`（语义） | 按你的硬约束执行；语义命名同时避免了「三套数字枚举并存」时的可读性陷阱，并补了 `rs-cancelled` 兜底（status=4 虽无用户入口，防数据异常时无样式） |

另：`prettyCode()`（3+3 分组）与 `STATUS_CLASS` 映射在 `Profile.vue` 与 `RedemptionsView.vue` 各有一份（各 3 行）。这是**刻意的**——本工程惯例就是各文件自持局部样式/工具（`.tabs`/`.status-tag` 同样如此），为一个 3 行函数新建公共模块反而破坏文件清单约定。

## 7. 已知局限（非缺陷，均已写入代码注释）

1. **分类 chips 是常量**：后端 `/shops` 的 `category` 为精确匹配且无枚举接口。管理员将来新增第 6 类时，该类会出现在「全部」里，但没有专属筛选 chip。
2. **「已过期」最多滞后 1 小时**：过期退分由后端每小时定时任务处理，前端刻意不做懒检测（GET 无副作用）。页面以「有效期至」提示用户自行判断，「刷新」按钮可手动重查。
3. **兑换弹窗的「有效期 30 天」是常量**：与 `.env` 的 `REDEMPTION_CODE_EXPIRE_DAYS` 对应；兑换成功后核销码弹窗会改用后端返回的真实 `expires_at`。
4. **商家端 9 个接口与管理端 7 个接口未封装**：属商家工作台/管理后台阶段，避免无用代码。
