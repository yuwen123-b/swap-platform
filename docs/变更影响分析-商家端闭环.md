## 二、现状核查（真实库 + 真实代码）

### 2.1 `user` 表 —— **没有 `role` 字段**（关键）

真实库 41 列，与角色/身份相关的只有一个 `status`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `phone` | varchar(11) UNIQUE | 登录账号 |
| `password_md5` / `salt` | varchar(32)/(16) | 登录凭证 |
| `nickname` | varchar(32) | |
| `points` | int, default 0 | **积分余额（唯一权威口径）** |
| `credit_score` | int, default 100 | 信用分 |
| `carbon_total` / `exchange_count` | decimal/int | 碳减排 / 交换次数 |
| `community` / `building` / `unit` / `room` | varchar | 住址 |
| `status` | tinyint, default 1 | 1=正常 0=封禁 |

**结论**：**不存在 `role` 字段，也不需要新增**。商家身份完全通过新表 `merchant.user_id` 反向关联（一个 user 账号既可以是普通用户、也可以是某家店的店主）。`GET /merchant/info` 就是「用 JWT 的 user_id 去 `merchant` 表反查」。

> 顺带说明：管理端是**另一套账号体系**（`admin` 表 + `create_admin_token`，payload 带 `type=admin`）。商家**不是**管理员，走的是用户侧 JWT（`create_token` / `get_current_user_id`）。两套 token 互不通用。

### 2.2 `points_log` 表

```
id / user_id / points / balance / source / related_id / description / created_at
UNIQUE KEY uk_points_log_source (source, related_id, user_id)
KEY idx_user_id (user_id)
```

三个必须记住的事实：

1. **`source=5` 已被定义为「兑换消耗」**（`app/core/constants.py::POINTS_SOURCE_LABEL`），可直接用，无需改枚举。
2. **唯一索引 `(source, related_id, user_id)` 是兑换幂等的天然闸门** —— 同一笔兑换单只可能写一条流水。（线上真实库该索引已存在；`sql/points_log.sql` 文件里另写了 `idx_user_created`/`idx_source` 两个索引，**线上实际没有**，但差异不影响本次功能。）
3. **`award_points` 不做余额校验**（见 2.5）。

### 2.3 `order` 表

`id / order_no(UNIQUE, varchar32) / item_id / buyer_id / seller_id / exchange_type(1购买2以物换物3赠送) / exchange_item_id / price / diff_points / diff_cash / status / meet_time / meet_location / completed_at / created_at`

**结论**：`order` 是「旧物互换/转让」订单，与「积分兑换商家服务」是**两种完全不同的业务**，不能复用。任务书新建 `redemption_order` 独立表是正确决策。订单号生成可复用 `app/services/order_service.py::generate_order_no()` 的形态（本次用 `RD` 前缀区分，见 3.3）。

### 2.4 路由挂载方式

`app/main.py`：

- **用户侧**：`_NEW_ROUTERS` 列表 → 每个 router **双前缀挂载**（`/api{X}` + `/api/v1{X}`）。`favorite`/`demand` 都复用了 `/user` 前缀。
- **管理端**：`admin_*.router` **只挂 `/api/admin`**，没有 `/api/v1/admin`。
- **响应外壳两套**：用户侧 `success()` → `{code:0, message, data}`；管理端 `ok()` → `{code:200, message, data}`。**不能混用**。
- **鉴权**：用户侧 `Depends(get_current_user_id)`；管理端 `Depends(require_role([...]))`（`app/routers/admin/deps.py`），角色 1=超管 2=运营 3=只读。

### 2.5 积分服务（`app/services/points_service.py`）

```python
award_points(cursor, user_id, points, source, related_id=None, description=None) -> int|None
```

- **不自开事务、不自取连接** —— 必须由调用方放进 `with connection() as conn` 里，与业务写入同事务。
- `points` 可为负数（扣分），`balance` 是 UPDATE 后**回读**的权威值。
- **⚠️ 它不做任何余额校验**，直接 `UPDATE user SET points=points+%s`。若传入的负数超过余额，**余额会变成负数**。
- 撞唯一索引 → 抛 `PointsAwardError`，全局处理器转 **409**。

### 2.6 其它可复用基建

| 能力 | 位置 | 本次用途 |
|---|---|---|
| 幂等迁移 | `pool.py::_ensure_column / _ensure_index / ensure_*()` | 建 5 张新表 |
| 签名静态资源 | `core/security.py::sign_file_path` + `api/v1/files.py` 白名单（jpg/jpeg/png/webp/gif） | `logo_url` / `image_url` 读取时现场签名 |
| 事务 | `pool.py::connection()` | 兑换/核销/结算 |
| 随机串 | `secrets` + `order_service.generate_order_no` | 兑换单号、核销码 |

## 三、表结构设计（5 张，全部走 `pool.py` 幂等迁移）

### 3.1 `merchant`

```sql
CREATE TABLE IF NOT EXISTS `merchant` (
  `id`              BIGINT NOT NULL AUTO_INCREMENT,
  `user_id`         BIGINT NULL COMMENT '关联的登录账号，可为空',
  `name`            VARCHAR(100) NOT NULL COMMENT '店铺名',
  `category`        VARCHAR(50) NULL COMMENT '类型：打印/便利店/理发/回收/家政',
  `contact`         VARCHAR(100) NULL COMMENT '联系方式',
  `address`         VARCHAR(200) NULL COMMENT '地址',
  `description`     TEXT NULL COMMENT '简介',
  `logo_url`        VARCHAR(500) NULL COMMENT 'LOGO 相对路径（读取时签名）',
  `status`          TINYINT NOT NULL DEFAULT 0 COMMENT '0待审核 1已通过 2已拒绝 3已停业',
  `commission_rate` DECIMAL(5,2) NOT NULL DEFAULT 5.00 COMMENT '平台佣金比例%',
  `created_at`      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_merchant_user` (`user_id`),          -- ★ 见第六节 Q4

```

### 4.4 核销的并发安全（必须条件 UPDATE）

```sql
UPDATE redemption_order
   SET status=2, redeemed_at=NOW()
 WHERE id=%s AND merchant_id=%s AND status=1 AND expires_at > NOW()
```

`rowcount=1` 才算成功；`rowcount=0` 时再查一次区分文案（不存在 / 非本店 / 已核销 / 已过期）。
**绝不能「先 SELECT 再 UPDATE」** —— 商家与用户同时点、或商家连点两次会造成双重核销。核销**不退积分、不动库存**。

### 4.5 兑换的并发安全（扣分 + 扣库存）

同一个 `with connection() as conn` 内：

1. `SELECT ... FROM merchant_product p JOIN merchant m ... WHERE p.id=%s AND p.status=1 AND m.status=1`（不存在 → 404）
2. `UPDATE merchant_product SET stock=stock-1, sold_count=sold_count+1 WHERE id=%s AND status=1 AND stock>0`
   → `rowcount=0` 即**库存不足，抛 400**（事务回滚，防超卖）
3. `INSERT INTO redemption_order (...)` → `lastrowid` 拿订单 id
4. **`SELECT points FROM user WHERE id=%s FOR UPDATE`** 校验 `points >= points_cost`，不足 → 400 回滚
5. `award_points(cursor, user_id, -points_cost, source=5, related_id=<订单id>, description=...)`

> 第 4 步的 `FOR UPDATE` 是**行锁**，用于堵住「两人同时兑换同一账号积分」的超扣。扣减动作本身仍由 `award_points` 完成（不自己写 UPDATE user.points）。

## 六、关键风险与缺口（★ 必须确认）

### Q1 ★★★ 积分与现金没有锚定汇率 —— 结算算不出「佣金金额」

`merchant_settlement.commission_amount` 是 **DECIMAL(10,2) 金额（元）**，但全库**没有任何「积分 → 元」的汇率**（`sys_config` 只有 `points_publish`/`points_exchange`/`carbon_per_exchange`）。

**不解决则 `POST /admin/merchant/settle` 无法产出 `commission_amount`。**

建议：新增配置 `MERCHANT_POINTS_TO_YUAN=0.01`（即 100 积分 = 1 元），佣金 = `points_total × 汇率 × commission_rate%`。

### Q2 ★★★ 过期未核销的订单，是否**退还积分**？

- 本项目 `points_log` 的 `source` 枚举里**没有「兑换退回」**这一项。
- 若沿用 `source=5, related_id=<同一订单id>` 退分 → **必然撞 `uk_points_log_source` 唯一索引，抛 409 且整笔回滚**。退分必须**新增枚举值**（如 `7=兑换退回`）并同步改 `POINTS_SOURCE_LABEL`。

建议（最省事、无副作用）：**不退分**，过期只把 `status` 刷成 3。用户权益受损需另行评估。

### Q3 ★★ `merchant_stats` 是否真的落表写入？

表结构里 `view_count` 需要「浏览埋点」，但本期**不做前端**，没有埋点来源。

建议：**建表但本期不写不读**，`/merchant/dashboard` 直接对 `redemption_order` 实时聚合（当前数据量极小，无性能问题）。埋点与缓存留到前端阶段再做。

### Q4 ★★ 一个用户账号能开几家店？

建议：**1 家**（`uk_merchant_user`）。同一账号重复申请走「被拒后可重提」逻辑而非新增记录。

### Q5 ★★ 路由歧义（脆弱点，本期不炸但需知晓）

`/merchant/{id}/products` 的 `{id}` 是**通配段**。FastAPI 用正则匹配，`/merchant/products/123` 这种请求**会先被 `/merchant/{id}/products` 吃掉**，然后因 `"products"` 转 int 失败返回 **422**，而**不会回退**到真正的静态路由。

本期接口里没有 `GET /merchant/products/{id}`，所以**实际安全**；但一旦以后新增「商品详情」接口，**必须**放到 `/merchant/products/detail/{id}` 这类不冲突的形态。

### Q6 ★ 商家 `logo_url` / 商品 `image_url` 的存法

项目铁律：**DB 只存相对路径，读取时现场签名**（签名 1 小时过期，落库即失效）。

建议：沿用同一口径，`logo_url` / `image_url` 存相对路径，接口返回时用 `sign_file_path()` 拼签名。种子数据（第七节）若不配图则留 NULL。

### Q7 ★ 管理端前缀

现有 admin 路由**只挂 `/api/admin`**，任务书要求 `/api/v1/admin/merchant`。

建议：**双挂载**（`/api/admin/merchant` + `/api/v1/admin/merchant`），与用户侧 `_NEW_ROUTERS` 保持一致，避免前端要记两套前缀规则。

### Q8 ★ 佣金比例以谁为准？

`merchant.commission_rate`（行级，默认 5.00）与 `.env MERCHANT_COMMISSION_RATE=5.00` 双份来源。

建议：**`.env` 只作为「入驻申请时写入的初始值」**，之后以 `merchant` 表那一行为准（管理员可对单店调整）。

## 七、模拟数据方案

任务书提示「纯 INSERT 会被 `initialize_schema` 全量重复执行」——正确。`sql/*.sql` 每次启动都会 `execute()` 一遍，纯 INSERT 会**每次启动都插 5 家店**。

**方案：走 `pool.py::ensure_merchant_seed()`**（`ensure_points_rules()` 同款）：

```python
# 存在性判断：以「店名」为准，已存在则整批跳过（绝不覆盖管理员改动）
SELECT COUNT(*) FROM merchant WHERE name IN (...)
# 不存在 → 一条多值 INSERT 插 5 家店（status=1）+ 一条多值 INSERT 插 10 个商品
```

5 家店 / 10 个商品（打印 50·80 / 便利店 30·100 / 理发 200·300 / 回收 50·0 / 家政 500·800 积分），`user_id` 全为 **NULL**（平台代录，不绑定任何真实账号，避免污染现有 12 个用户的身份）。

> 若单店重复触发，用 `INSERT IGNORE` 会因无唯一键而失效，因此**必须**用「先 COUNT 再插」的存在性判断。
