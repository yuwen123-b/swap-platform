# 《现状报告》：交易方式「掏钱」+ AI 估价后直接发布

> 仅调研，代码零改动。所有结论均来自真实文件与真实库（information_schema）实测。

## 0. 一句话结论

**数据库字段（item.exchange_mode / item.price、order.exchange_type / price / diff_points / diff_cash、item.original_price / condition_level）全部已存在，无需任何迁移。**
真正缺的只有三处：① 发布接口写死 `exchange_mode=1` 不收用户选择；② order 表那几个金额列是「沉睡字段」，全项目无任何读写；③ 仓库里**没有 Publish.vue，也没有 /publish 路由**——发布入口是 ItemList.vue 的弹窗。

## A. 交易方式现状

### A1. item 表有 exchange_mode 吗？取值范围与含义？

有。实测：

| 列 | 类型 | 默认 | 列注释 |
|---|---|---|---|
| `exchange_mode` | tinyint | 1 | 交换模式：1=免费送 2=等价互换 3=低价转让 |
| `price` | decimal(10,2) | 0.00 | 转让价格 |
| `original_price` | decimal(10,2) | 0.00 | 原价 |
| `condition_level` | tinyint | 0 | 成色：1~5 |
| `expected_item` | varchar(100) | NULL | 期望换物类型 |

前端口径：`1=赠送 2=交换 3=低价转让`（ItemList.vue 与 ItemDetail.vue 的 `MODE_TEXT`、列表页筛选下拉「赠送/交换/低价转让」三选项）。

**关键现状**：`POST /items`（app/api/v1/item.py:275-282）INSERT 时**硬编码 `exchange_mode=1`、`condition_level=0`**：

```sql
INSERT INTO item (user_id, category_id, title, description, images,
                  expected_item, contact, status, exchange_mode, condition_level)
VALUES (%s,%s,%s,%s,%s,%s,%s, 4, 1, 0)
```

→ 当前**所有用户发布的物品都是「赠送」**，`price` 从不写入（保持 0.00）；发布弹窗也没有交易方式选择器。列表页能按 3 种模式**筛选**，但发不出 mode=2/3 的物品。

### A2. 前端发布页有哪些交易方式选项？

**没有任何交易方式选项。**

- 发布入口 = `ItemList.vue` 的「上传物品」`el-dialog`（第 125-176 行），仓库**不存在 Publish.vue**，路由表也没有 `/publish`。
- 弹窗字段：物品名称、物品描述、物品图片（ImageUploader）、分类（下拉取 `category_id`）、期望交换物品（`expected_exchange`）、联系方式。
- 提交走 `POST /items` 的 multipart，`uploadItem(formData)`。

### A3. 详情页「我要换」现在怎么处理？区分赠送/交换/购买吗？

**不区分。** 只有一个按钮：

```
canSwap = 物品存在 && status === 1 && 非本人
→ <el-button>我要换</el-button>   // 文案固定，点开「发起交换」弹窗，调 createOrder(itemId, message)
```

唯一的「模式感知」在 facts 区（ItemDetail.vue:83）：

```html
<span v-if="item.exchange_mode === 3" class="chip chip-peach">¥ {{ item.price }}</span>
```

即 mode=3 时才展示一个价格 chip，但按钮文案与交互完全一样。`createOrder` 只传 `item_id + message`，价格不参与下单。

### A4. order 表有 price / diff_points / diff_cash 吗？现在用到没？

都有，但**全部未被任何代码写入或读取**（"沉睡字段"）：

| 列 | 类型 | 默认 | 列注释 |
|---|---|---|---|
| `exchange_type` | tinyint | 1 | 类型：1=购买 2=以物换物 3=赠送 |
| `exchange_item_id` | bigint | NULL | 换出物品ID |
| `price` | decimal(10,2) | 0.00 | 成交金额 |
| `diff_points` | int | 0 | 补差积分 |
| `diff_cash` | decimal(10,2) | 0.00 | 补差现金 |

实测证据：`POST /orders` 的 INSERT 列清单只有 `(order_no, item_id, buyer_id, seller_id, exchange_type, status, created_at)`；列表/详情 SQL 均未 SELECT 这些列；前端也不展示。→ 需求 1 可直接启用，**无需加列**。

### A5. order.exchange_type 取值范围与含义？

DB 列注释 + 代码常量 + 测试三者一致：

```
order.exchange_type：1=购买  2=以物换物  3=赠送
```

`app/api/v1/order.py:85`：

```python
EXCHANGE_TYPE_BY_MODE = {1: 3, 2: 2, 3: 1}   # item.mode → order.type
DEFAULT_EXCHANGE_TYPE = 2
```

即：item mode1(赠送)→type3(赠送)、mode2(交换)→type2(以物换物)、**mode3(低价转让)→type1(购买)**。

> ⚠️ **重要冲突**：任务书里写的 `order.exchange_type = 1=赠送 / 2=交换 / 3=购买`，与现网**正好相反**。
> 现网是 `1=购买 / 2=以物换物 / 3=赠送`（DB 列注释、代码、`tests/test_user_orders.py:405` 的断言 `EXCHANGE_TYPE_BY_MODE == {1:3, 2:2, 3:1}` 三方一致）。
> **建议沿用现网语义**：`EXCHANGE_TYPE_BY_MODE` 一行不动，"出售"映射到 type=1(购买) **已经天然正确**。若按任务书翻转，会同时破坏既有赠送/交换语义 + 让现有测试失败（违反"不破坏现有赠送/交换逻辑"约束）。

## B. AI 估价现状

### B1. Pricing.vue 估价成功后有什么后续操作？

只有两件事：`result.value = await pricing({...form})` 渲染结果卡 + `loadHistory()` 刷新「最近定价记录」。
**没有任何"发布 / 保存 / 分享"入口**——估价是孤岛。

### B2. 估价结果包含哪些字段？

后端 `POST /ai/pricing`（app/api/v1/ai.py:29-45）返回三个字段：

```
suggested_price     建议售价（Decimal，2 位小数）
depreciation_rate   折旧率（0.10 ~ 0.90）
pricing_reason      中文解释文案
```

- **没有价格区间**（无 min/max），是单一确定值。
- 算法是**纯公式**（`成色系数 + 分类调整`），**非大模型生成**，因此结果稳定、可复现。
- 请求侧字段（PricingRequest）：`item_name` / `description` / `item_category`（**字符串**）/ `condition_level`(1-5) / `original_price`。
- 另有 `GET /ai/pricing/history` 读 `ai_pricing_log` 表。

### B3. 估价结果能不能传到发布页？手动还是自动？

**不能传，也无法自动。** Pricing.vue 与发布弹窗之间：没有共享 pinia store、没有 query、没有 sessionStorage，**完全隔离**。用户只能自己记下价格再手填。且发布页没有独立路由，`/publish?from=pricing` 无落点。

### B4. 发布页表单字段有哪些？和估价结果能对应上吗？

| 估价侧字段 | 发布弹窗字段 | 对应性 |
|---|---|---|
| `item_name` | `title` | ✅ 直接对应 |
| `description` | `description` | ✅ 直接对应 |
| 图片 `imageFile`(File) | `image`(File) | ✅ 可用 store 传 File 对象 |
| `condition_level`(1-5) | —— | ❌ **发布页没有成色字段**，后端也硬编码 `condition_level=0` |
| `original_price` | —— | ❌ **发布页没有原价字段**，后端 INSERT 不写 `original_price` |
| `item_category`（中文名，如"数码电子"） | `category_id`（**数字ID**，来自 /categories） | ⚠️ **需要一次「中文名 → 分类ID」映射**，这是需求 2 的主要难点 |
| `suggested_price` | —— | 发布前无对应（对应 `item.price`，仅出售模式有意义） |

## C. sys_config 现状（交易方式/积分相关键）

实测 `sys_config` 全部键：

| config_key | config_value | 说明 |
|---|---|---|
| announcement | ... | 平台公告 |
| audit_enabled | 1 | 物品发布是否需要审核 |
| carbon_per_exchange | 5.0 | 每次完成交换折算碳减排量 |
| contact | 400-800-1234 | 客服联系方式 |
| platform_name | ... | 平台名称 |
| points_exchange | 20 | 完成一次交换奖励积分 |
| points_publish | 10 | 发布物品奖励积分 |
| points_report_deduct | 50 | 举报成立扣除积分 |

→ **不存在** `points_publish_give` / `points_publish_swap` / `points_publish_sell`，也**不存在任何交易方式相关键**。
现有发奖路径：审核通过（admin/items audit）→ `SOURCE_PUBLISH`（points_log.source=1）发 `points_publish`；交换完成 → `SOURCE_EXCHANGE`（=2）发 `points_exchange`。两条路径都**不看 exchange_mode**。

## D. 需要你拍板的 6 个点

1. **order.exchange_type 枚举方向**（最重要）
   任务书假设「1赠2换3买」与现网「1买2换3赠」相反。**建议沿用现网**，映射表不动，既有 229 测试与赠送/交换逻辑零影响。

2. **需求 2 的目标页**
   没有 Publish.vue / 没有 /publish 路由。二选一：
   - **(a) 复用 ItemList 发布弹窗**（推荐）：`from=pricing` 时自动打开弹窗并预填，改动最小、天然满足"不动 Hero/网格/ProfileSubLayout"。
   - (b) 新建独立 `Publish.vue` + `/publish` 路由：更贴合任务书原文，但新增页面与路由。

3. **成色 / 原价缺口**
   发布页目前不收 `condition_level` / `original_price`。若希望估价结果把成色、原价也带过去，需给 `POST /items` 增两个**可选** Form 字段（DB 列已存在，零迁移）。

4. **分类 中文名 → ID 映射**
   估价的 `item_category` 是中文名，发布要 `category_id`。计划：按 `category.name` 查表；查不到时预填为空并提示"请手动选择分类"，不猜不造。

5. **积分区分规则（建议第 1 批先不做）**
   要"赠送高 / 交换正常 / 出售低"必须新增 sys_config 键并改发奖逻辑，会触碰 admin 审核发奖路径（历史教训：发奖逻辑两处实现易漂移）。**建议：第 1 批只做交易方式本身，积分区分单独作为第 3 批**，你确认后再动。

6. **价格落库与校验**
   任务书写 0.01–99999；DB 是 `DECIMAL(10,2)`。计划：后端用 `Decimal` + 范围校验，`exchange_mode≠3` 时强制 price=0；前端 `el-input-number(0.01~99999, 2位)`。

## E. 两批实现计划（待确认后执行）

### 第 1 批：需求 1「掏钱」交易方式

**后端（不改列，全复用）**
- `POST /items` 增 `exchange_mode: int = Form(1)`、`price: str = Form("")`；校验 mode∈{1,2,3}；mode=3 时 price 必填且 ∈[0.01, 99999]（Decimal(10,2)），mode≠3 时 price 落 0；INSERT 写入 `exchange_mode` / `price` / `expected_item`（`condition_level` 视第 3 点决定）。
- `GET /items/{id}` 已是 `SELECT *`，天然返回 exchange_mode/price（仅加整形：mode≠3 时 price 归 0，避免误解）。
- `POST /orders`：读 `item.price`，出售单把 `order.price = item.price` 落库；`exchange_type` 映射保持不变。
- `PUT /orders/{id}/complete`：不改发奖（积分区分留第 3 批）。
- **清单/详情返回价格**：`OrderListItem` / `OrderDetail` 增 `price` / `exchange_type` 字段，SQL 补 SELECT。

**前端**
- ItemList 发布弹窗：加「赠送 / 交换 / 出售」三选（默认赠送）；选出售显示「售价」输入；选交换显示「期望交换物品」；赠送无需额外字段。
- ItemDetail：按 mode 换按钮文案 —— 赠送→「我想要（免费领取）」、交换→「我要换」、出售→「我要买 ¥xx」；出售价格醒目。
- ExchangesView：列表/详情展示价格（仅出售单）。

**验证**：pytest 全绿（改造 `test_user_orders.py` / `test_item_api.py` 并新增用例）→ vite build → `@vue/compiler-sfc` 编译校验 → 真实库端到端 → 输出《验证清单》。

### 第 2 批：需求 2「估价后直接发布」

- 新增 `src/store/publishDraft.js`（pinia，**已装 pinia 2.3，零新依赖**）。

- 发布侧读 draft 预填：图片(File)、名称、描述、分类（name→id 映射）、成色、原价、售价；用户确认/修改后提交；提交或关闭后清空 draft。
- 后端：**无改动**（复用 `POST /items`）。
