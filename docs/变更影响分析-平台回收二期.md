## 零、一句话结论

**数据模型 100% 无冲突（2 张新表 + item 2 列都是净新增），但有 3 处会直接导致功能不可用的硬冲突必须改方案**：

1. `POST /items` 落库固定 `status=4`（待审核），而任务书的回收接口要求 `status=1` → **「发布即回收」100% 报 400**；
2. 任务书的发分步骤排在建单之前 → `related_id` 拿不到值 → **绕过 `points_log` 唯一索引，并发双击可双倍发分**；
3. 取消退还若沿用 `source=8` + 同一 `related_id` → **必然撞 `uk_points_log_source`，取消功能 100% 失败**（409）。

另有 3 处**接口缺口**（任务书清单里没有、但功能跑不起来必须补）：估价预览接口、销售记录查询接口、回收商下拉数据源。

以上 6 项我都给了落地方案，**全部按推荐执行即可一次跑通**，不需要你改业务设计。

## 三、数据模型（按任务书 + 2 处必要修正）

### 3.1 `item` 补 2 列

按任务书原文，走 `pool.py` 的 `_ensure_column`（幂等，`information_schema` 存在性判断）：

```python
_ensure_column(cursor, "item", "accept_points",
               "accept_points INT NOT NULL DEFAULT 0 COMMENT '平台回收估价，0表示不参与回收'")
_ensure_column(cursor, "item", "recycle_status",
               "recycle_status TINYINT NOT NULL DEFAULT 0 COMMENT '0不参与 1待取件 2已入库 3已售出 4已取消'")
```

★ **修正 1**：任务书写 `INT DEFAULT 0`（可空）。改为 `NOT NULL DEFAULT 0` —— 既可空会让 `accept_points IS NULL` 与「0=不参与」两种语义并存，前端要判两次。`recycle_status` 同理。

### 3.2 `platform_recycle` / `platform_sale`

建表语句按任务书原文落地，只做两处**索引补强**（写法与既有 `volunteer_task` / `favorite` 的内联 KEY 一致）：

| 表 | 任务书索引 | 建议补充 | 理由 |
|---|---|---|---|
| `platform_recycle` | `idx_user(user_id,status)`、`idx_status(status)` | `uk_recycle_no(recycle_no)` 走**列内 UNIQUE**（任务书已写）；再补 `idx_created(id)` 不需要（PK 即序） | — |
| `platform_sale` | `idx_recycler(recycler_id)` | 补 `KEY idx_created_at(created_at)` | 销售记录列表按时间倒序 + 统计按时间区间过滤 |

**迁移落点（关键）**：**绝不能**写进 `sql/*.sql`。原因（`pool.py` 里已有三处同类说明）：`initialize_schema()` 每次启动把 `sql/*.sql` 全量再执行一遍、每个文件只 `execute()` 一次（**单文件只能一条语句**）、且**没有 try/except**（第二次启动会因 `Duplicate column` 直接让后端起不来）。因此统一放进 `pool.py` 新增的 `ensure_recycle_tables()`，并在 `main.py` 的 `startup()` 里排在 `ensure_merchant_seed()` 之后。

### 3.3 语义落点表（避免实现时再猜）

| 字段 | 取值 | 说明 |
|---|---|---|
| `item.accept_points` | 0 / 10-500 | 0 = 不参与回收 |
| `item.recycle_status` | 0/1/2/3/4 | 与 `platform_recycle.status` 同序同步 |
| `item.status` | 提交回收 → **2**（已下架，从「闲」列表消失，F8）；取消 → **回 1** | 见 D6 |

## 四、后端接口设计（含 6 处任务书修正）

### 4.1 用户端

#### ① `PUT /api/v1/items/{id}/recycle`（落在 `item.py`）

**任务书逻辑顺序有误（必修）**。任务书写 `c. 立即给积分 → d. 创建 platform_recycle 记录`，但：

```python
award_points(cursor, user_id, points, source=8, related_id=??, ...)
```

`related_id` 必须在发分时就有值。若反过来先发分，只能写 `related_id=NULL` 或 `item.id`：
- **`related_id=NULL`** → MySQL 唯一索引**不约束 NULL**（`pool.py:293` 有明确说明）→ **唯一索引这道闸完全失效**，并发双击可双倍发分；
- **`related_id=item.id`** → 该物品取消后重新提交回收会撞唯一键（同一 item 两次回收）。

**修正后的顺序（必须严格按此）**：

```
a. SELECT item（校验：属于当前用户 AND status IN (1,4) AND recycle_status IN (0,4)）
b. 成色取值：condition_level 缺失/非法 → 0 档
c. 算 accept_points = estimate_points(condition_level)   ← 纯函数，服务端算，绝不接受前端传值
d. UPDATE item SET exchange_mode=4, accept_points=?, recycle_status=1, status=2
      -- 条件更新 WHERE id=%s AND user_id=%s AND status IN (1,4) AND recycle_status IN (0,4)
      -- rowcount=0 → 400「该物品已在回收流程中」
e. INSERT platform_recycle (...) → recycle_id = lastrowid
f. award_points(cursor, user_id, accept_points, source=8, related_id=recycle_id,
                description=f"平台回收「{title}」")   ← related_id 用回收单 id
g. 回读余额，返回 { recycle_no, points_reward, remaining_points, pickup_method }
```

**修正 2（★ 关键）**：`status IN (1,4)` —— 这是 D3。`POST /items` 落库是 4（F7），只允许 1 会让「发布即回收」100% 报 400。

**修正 3**：`exchange_mode` 一并置 4（D5），否则列表卡片标签会显示「免费送」。

**修正 4**：`condition_level` 服务端自行读库（`SELECT condition_level FROM item`），**不接受前端传 `accept_points`** —— 否则用户可以伪造 500 分。

#### ② `GET /api/v1/recycle/estimate`（★ 新增，任务书缺）

```
GET /api/v1/recycle/estimate?condition_level=4
→ { condition_level: 4, estimate_points: 220, min: 10, max: 500 }
```

**为什么必须新增**：任务书要求弹窗「显示系统估价（如 40 积分）」——这是**提交前**的预览，而 `POST /items` 那一刻才有 item_id，`PUT /recycle` 又必须提交后才有 id。**没有只读接口，弹窗就只能把公式抄一份到 JS 里**。两份公式一旦漂移（用户看到 40、实际到账 35）就是投诉级 bug，且违反项目一贯的「单一真源」做法。

**落点选择**：放在**新 router** `api/v1/recycle.py` 的 `/estimate`，**不放** `item.py` 的 `/items/recycle/estimate` —— 后者必须声明在 `@router.get("/{item_id}")` **之前**才不会被吞（`{item_id}` 会匹配到 `recycle` 这个字符串，然后 Pydantic 转 int 失败 → 422）。放在新 router 从根上消除这个坑。

#### ③ `GET /api/v1/recycle/my`、④ `PUT /api/v1/recycle/{id}/cancel`

按任务书。`/my` 支持 `status` 筛选 + `page/size`，JOIN `item` 取标题与首图（`item.images` 是 JSON 列，按既有 `_parse_images` 同思路解析，解析失败降级空列表，不让脏数据把接口打 500）。

**取消（`PUT /recycle/{id}/cancel`）必须用 `source=9`（D2）**：

```
条件更新 platform_recycle SET status=4 WHERE id=%s AND user_id=%s AND status=1
rowcount=0 → 400（已入库/已售出/已取消，不可撤销）
同步 item：SET recycle_status=4, status=1（见 D6）
award_points(cursor, user_id, +points_reward, source=SOURCE_RECYCLE_CANCEL, related_id=recycle_id,
             description="平台回收取消退还")
```

★ **修正 5（必修）**：任务书只让新增 `8: '平台回收所得'`。若取消退还也写 `source=8`，那么 `(8, recycle_id, user_id)` **已经存在**（提交时写过）→ 必然命中 `uk_points_log_source` → `PointsAwardError` → 全局处理器返回 **409**，**取消功能 100% 失败**。

这不是新发明：既有 `SOURCE_REDEEM=5`（兑换消耗）与 `SOURCE_REDEEM_REFUND=7`（兑换过期退还）**就是同一个套路**，`pool.py:74-77` 和 `merchant_service.py:482-484` 都有注释说明「用不同 source 才能让同一笔业务同时存在消耗与退还两条流水」。故新增 **`9: '平台回收取消退还'`**。

### 4.2 运营端（`app/routers/admin/recycle.py`，挂 `/api/admin/recycle`）

| # | 接口 | 权限 | 要点 |
|---|---|---|---|
| ⑤ | `GET /list` | read `[1,2,3]` | `status` 筛 + 分页；JOIN `item`（标题/首图）+ `user`（昵称）；`LIMIT` 上限 100 |
| ⑥ | `PUT /{id}/receive` | write `[1,2]` | 条件更新 `WHERE id=%s AND status=1`；`rowcount=0` → 400「该回收单不在待取件状态」；同步 `item.recycle_status=2` |
| ⑦ | `POST /sell` | write `[1,2]` | 见下方并发设计 |

**`POST /sell` 单事务 + 并发设计（★ 唯一一处必须做对的地方）**：

```
a. 参数校验：recycle_ids 非空、去重、≤100 条；total_amount = Decimal，> 0 且 ≤ 99999999.99
b. 校验回收商：merchant WHERE id=%s AND category='回收' AND status=1 → 否则 400
c. 一次性锁定：SELECT id FROM platform_recycle WHERE id IN (...) FOR UPDATE
     → 查到的行数 ≠ 请求条数 → 400「部分回收单不存在」
     → 任一行 status != 2 → 400「回收单 XXX 不在已入库状态」（附单号）
d. INSERT platform_sale（sale_no / recycler_id / total_amount / item_count / items_json）
e. 条件更新：UPDATE platform_recycle SET status=3, sold_at=NOW()
      WHERE id IN (...) AND status=2
     → rowcount != item_count → 抛错，整笔回滚（并发下另一运营已卖掉其中一单）
f. UPDATE item SET recycle_status=3 WHERE id IN (对应的 item_id)   ← 同步物品侧
g. 返回 { sale_no, total_amount, item_count }
```

★ **修正 6**：任务书步骤 c 只更新 `platform_recycle`，**漏了同步 `item.recycle_status=3`**。不同步的话 `item.recycle_status` 会永远停在 2，物品侧再也撤不回来。

**金额精度**：全程 `Decimal` + `ROUND_HALF_UP` 量化到 2 位后再写 `DECIMAL(10,2)`。项目里有前车之鉴（阶段三佣金断言曾踩过 `float round(0.155,2)=0.15` vs `Decimal HALF_UP=0.16`）。

### 4.3 `/stats` 统计口径（默认按此，有异议请指出）

| 字段 | 口径 |
|---|---|
| `total_received` | `platform_recycle` 中 `status IN (2,3)` 的条数（**曾入库过**；已售出也算入过库） |
| `total_sold` | `status=3` 的条数 |
| `total_points_issued` | `SUM(points_reward) WHERE status IN (1,2,3)` —— **排除已取消**（取消已退回，计入成本会虚高） |
| `total_revenue` | `SUM(platform_sale.total_amount)` |
| `total_cost` | `total_points_issued × points_to_yuan`，Decimal HALF_UP 到 2 位 |
| `gross_profit` | `total_revenue - total_cost`（**允许为负** —— 库存还没卖出时就是负毛利，这是真实经营状态，不做 clamp） |
| `points_to_yuan` | ★ 额外透出，取 `settings.merchant_points_to_yuan`（与商家结算同源，F6） |
| `pending_pickup` | `status=1` 条数（运营要看的待办量） |
| `status_distribution` | 4 状态计数数组（看板「物品状态分布」） |
| `top_recyclers` | `platform_sale GROUP BY recycler_id` → `SUM(total_amount)`、`COUNT(*)`、`SUM(item_count)`，按金额倒序 TOP 10（看板「回收商贡献排行」） |

★ 后 3 个字段是**纯新增**（不影响任务书要求的 6 个字段），因为任务书本身要求看板展示「物品状态分布 + 回收商贡献排行」，而 `/stats` 里没有这两项数据 —— 不扩展就得再加一个接口。

**汇率不硬编码 1 元/100 分**：改用 `settings.merchant_points_to_yuan`。若哪天平台调汇率，回收成本与商家结算不会各说各话。
