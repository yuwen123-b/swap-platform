# 可行性报告：360° 查看器「深度视差」效果

> 结论先行：**技术可行，推荐「本地 ONNX 深度估计 + 自定义 shader 视差」组合**；
> 但有一个必须先讲清楚的前提问题 —— **当前 4 张视角图本身就不是同一物体**，
> 深度视差只能让"每张图内部"更立体，**治不了"翻图片"的根因**。

---

## 一、四个现状问题的回答

### 1. Three.js 版本

`agent_front/package.json`：`three ^0.186.1`，实际安装 **0.186.1**。
- 支持 WebGL2 / GLSL ES 3.0，`onBeforeCompile` 注入自定义 shader 片段是官方稳定 API；
- ⚠️ `MeshBasicMaterial` **不支持 `displacementMap`**（该属性只存在于
  MeshStandardMaterial / Phong / Lambert / Matcap 等带光照的材质上）。
  现有查看器用的是 MeshBasicMaterial（无光照、恒定外观，是第 7 批特意定下的），
  换成带光照材质会整体改变画面观感，**displacementMap 方案直接排除**。

### 2. 有没有可用的深度估计模型？

**远端 API：三个来源逐一核查，结论是没有可靠的。**

| 来源 | 核查结果 |
|---|---|
| `.env` 配置 | 无任何深度估计相关键。现有：image-edit / t2i / TTS / ASR / VL / embedding |
| 百炼 DashScope | 模型清单（2026-09 版）覆盖 文本/图像/3D/音频/全模态/向量，**无单目深度估计模型** |
| 魔搭 ModelScope | Depth-Anything-V2 **模型仓库存在**，但 HF 版 README 明确 `inference: false`；API-Inference 免费托管清单只覆盖 LLM / VL / 文生图 / 语音，**没有深度估计 REST 接口**。且上一批已实测魔搭 `/v1/images/edits` 返回 404，其图像接口覆盖面本就存疑 |

**本地推理：可行，且是唯一可靠路径。** Depth Anything V2 Small 有官方 ONNX 导出
（Apache-2.0，onnx-community / depth-anything 组织），输入 518×518，输出预测深度图，
CPU 上用 onnxruntime 跑即可。项目约束也明说"除非必要，如 onnxruntime"——这里就是"必要"场景。

### 3. CPU 环境跑 Depth Anything Small 需要多久？

公开 benchmark（onnxruntime CPU，ViT-S，518×518，fp32）：

| 精度 | 单帧耗时（参考台式机） | 普通笔记本 CPU 估算 |
|---|---|---|
| fp32（99MB） | ~122ms | 0.5 – 2s |
| int8 量化（25MB） | ~107ms（量化反而更快） | 0.3 – 1.5s |

**一张图 ≤ 2s，4 张视角图全流程 ≈ 1 – 8s，远低于 10s/张的约束上限。**
首次运行还有一次性成本：onnxruntime session 加载 + 模型文件下载（见下）。

### 4. 能否在物品发布时异步生成深度图？

**可以，且架构上是顺水推舟：**
- 发布/重新生成都走 `BackgroundTasks → panorama_service.run_generate`（线程池执行，
  不占请求线程、不引入 Celery）；
- 深度图生成**挂在 `run_generate` 尾部**：视角图 ready → 逐张跑深度 → 存
  `uploads/items/{id}/depths/{front,left,back,right}.jpg`（灰度 JPEG）；
- `GET /panorama/{id}` 的返回增加 `depth_views`：深度图结果**直接存进
  `panorama_views` 这个 JSON 文本列的 payload 里**（新增 `depths` 键），
  **零数据库迁移**；生成失败或未生成时 `depth_views: null`，前端自动降级；
- 深度图用灰度 JPEG（质量 80、512×512）而不是 PNG：深度图是平滑渐变，
  有损压缩几乎无视觉损失，4 张合计 **≈ 150 – 250KB**，满足 <500KB 预算
  （无损 PNG 同尺寸要 ~1MB，超预算）。

### 需要新增的依赖（一次性）

| 项 | 体积 | 说明 |
|---|---|---|
| `onnxruntime`（CPU 版） | wheel ~60MB | 用户约束中点名的例外项 |
| `numpy` | wheel ~15MB | onnxruntime 的前置，预处理必需 |
| 模型文件 int8 ONNX | ~25MB | 首次运行从 hf-mirror.com 下载到 `agent_back/models/`，需手动/脚本执行一次 |

## 二、必须先说清的前提问题（重要）

**深度视差 ≠ 修复"翻图片"。** 我抽查了真实库现有产物（item 73）：

- `front.jpg`：奶油白 L 形皮沙发，白底商品图（这是用户上传的原图）；
- `right.jpg`：**完全不同的棕色布艺沙发**，不同颜色、不同款式、特写构图。

也就是说，第 10 批《效果诊断报告》定位的问题（魔搭 image-edit 404 → 降级文生图重画）
**至今未修**，4 张视角图在多数情况下是"各画各的"，几何上互不衔接。

深度视差的效果是：**在单张图内部**，让近处物体相对背景产生位移，
产生"这画面有厚度"的感觉。它**不能**让四张互不相关的图变得像"转一个物体"——
跨图切换时的跳变依然存在，甚至因为每张图有了立体感，切换瞬间反而更显突兀。

**诚实的预期管理：**
1. 若视角链路仍是降级文生图，深度视差的收益 = 每张图"鼓起来"，翻页感不变；
2. 视角图多为**白底商品图**，Depth Anything 在这类图上的深度主要是"物体 vs 背景"
   的二段分离 —— 这恰好是视差最能出效果的地方（主体凸出、背景后退），
   但物体内部的立体层次有限；
3. 若先把第 10 批的视角一致性修好（方案 A/B），深度视差才有完整的发挥空间。
   **建议顺序：先修视角生成（第 10 批决策），再上深度视差；或两者同批做、
   深度视差作为视角修好前的"半成品体验"。**

## 三、前端两种实现方案对比

| | 方案 A：分层 PNG（3-5 层透明图叠加） | 方案 B：shader 视差（推荐） |
|---|---|---|
| 原理 | 后端按深度阈值把每张图切成 N 张带 alpha 的层图，前端 N 个 Plane 以不同速度水平偏移 | 后端只出 1 张灰度深度图；前端 `onBeforeCompile` 注入视差 UV 偏移，按深度 + 视线方向逐像素采样 |
| 后端改动 | 需再做一次"切片"处理（PIL 逐层抠图+alpha），产物 4×N 张 | 只多存 4 张灰度 JPEG |
| 产物体积 | RGBA PNG 4×N 张，512px 下也要 **~800KB-2MB**，超预算；除非再降清晰度 | **~200KB** |
| 视觉效果 | 纸片剪贴感明显，层边缘锯齿/白边，层数少时阶梯感强 | 逐像素平滑视差，是真正意义上的"视差映射"；幅度可控 |
| 前端改动 | 场景里每视角 N 个 Mesh，管理复杂；overdraw 填充率 ×N | 每个 material 注入 ~40 行 shader；4 个 Mesh 不变 |
| 性能 | N 倍 overdraw，移动端有压力 | 每像素多 1 次纹理采样 + 几条算术指令，**可忽略** |
| 降级 | 缺层图需逐层判断 | 深度贴图加载失败 → 不注入/置零偏移，自动回到现状 |

**推荐方案 B（shader 视差）**。技术要点：
- 在现有 `MeshBasicMaterial` 上用 `onBeforeCompile` 注入，**不换材质、不加光照**，
  保住第 7/8 批定下的全部观感与几何结论（PANEL_H=14.4、overscan 等全部不动）；
- 每个面片把自己的世界朝向（4 个面是解析已知的）作为 uniform 传入，
  vertex 阶段算出**物体空间视线方向**，fragment 阶段用深度图做 1-2 步视差偏移；
- 视差幅度 uniform 化（默认 ~0.05，可调/可关），幅度取小避免边缘拉伸；
- 深度贴图 `LinearFilter` + 需要 `wrapS=ClampToEdge`（与现有 overscan 逻辑对齐）；
- **降级链**：`depth_views` 为 null / 深度图 404 / WebGL 异常 → 保持现状
  MeshBasicMaterial 不注入，零副作用。拖拽、俯仰、原图切换、助老/高对比度模式全部不受影响（纯片元级改动）；
- 预期帧率：4 个 plane、单纹理采样，桌面/移动端均 ≥60fps，远高于 30fps 约束。

## 四、实现方案概要（确认后执行）

### 后端（新增 `app/services/depth_service.py`）
1. `estimate(image_path) -> Path`：PIL 读图 → 518×518 预处理（ImageNet mean/std）→
   onnxruntime session 推理 → 深度归一化 → 反量化 8bit 灰度 → 512×512 JPEG 存
   `uploads/items/{id}/depths/{name}.jpg`；
2. session 单例（首次调用惰性加载 int8 模型，模型文件缺失时整体静默跳过 = 优雅降级）；
3. `panorama_service.run_generate` 在视角图 ready 后调用 `run_depths(item_id)`：
   4 张全成功 → payload 写入 `depths` 键；任一失败 → 不写，status 仍 ready；
4. `get_views` / `get_item` 读取时对 depth URL 补 HMAC 签名（与视角图同规则）；
5. 新增配置键：`DEPTH_MODEL_PATH`（默认 `models/depth_anything_v2_vits_int8.onnx`）、
   `DEPTH_ENABLED`（默认 true，一键关闭）。

### 前端（`PanoramaViewer.vue`）
1. props 增加 `depthViews`（可选）；有值时给每个 material 走"注入版"构建；
2. 深度图随视角图一起 TextureLoader 加载，加载成功前材质保持原样（先平面后立体，无闪烁）；
3. 视差幅度 uniform，双击回正/自动旋转逻辑零改动。

### 测试
- 后端：depth_service 单测（模型缺失跳过、尺寸/格式、归一化）+ panorama payload 带 depths 的
  读取签名测试（mock 推理，不真跑模型，避免 CI 依赖 25MB 文件）；
- 前端：`@vue/compiler-sfc` 编译 + 结构断言；`vite build`；
- 真实库端到端：对现有 item 55/73 跑一次真实推理，确认产物、体积、接口返回、降级链路。

### 工作量预估
后端 ~200 行 + 前端 ~120 行 + 测试；新增依赖仅 onnxruntime + numpy。

## 五、风险清单

| 风险 | 缓解 |
|---|---|
| 视角图本身不一致（当前降级链路） | 报告第二节已说明；效果打折但功能不受损，视角修好后自动受益 |
| HF 下载模型需外网 | 提供 hf-mirror.com 镜像地址；模型缺失=功能整体静默关闭 |
| onnxruntime 首次 session 加载 ~1s | 惰性单例，只发生在后台任务，不碰请求路径 |
| 白底商品图深度层次有限 | 视差幅度默认取小值（0.05），主要呈现"主体-背景"分离 |
| CPU 慢机器上 4 张 >10s | 挂在 BackgroundTasks 异步执行，不阻塞任何请求；depths 未就绪=前端平面显示 |
