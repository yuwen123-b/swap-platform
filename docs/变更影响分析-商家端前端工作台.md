## 三、你问的 5 个问题，直接答案

### 1. `/api/v1/merchant` 下哪些是商家专用的

| 路径 | 方法 | 商家专用 | 权限门槛（`require_merchant`） |
|---|---|---|---|
| `/apply` | POST | 是 | 登录即可（未入驻/被拒可重提） |
| `/info` | GET | 是 | 登录即可（未入驻返回 `{merchant: null}`） |
| `/products` | GET | 是 | 登录 + **有店**（未过审也能看，用于展示"审核中"） |
| `/products` | POST | 是 | 登录 + 有店 + **已过审** |
| `/products/{id}` | PUT | 是 | 登录 + 有店 + **已过审** |
| `/products/{id}/offline` | PUT | 是 | 登录 + 有店 |
| `/redemptions` | GET | 是 | 登录 + 有店 |
| `/redemptions/verify` | POST | 是 | 登录 + 有店 + **已过审** |
| `/dashboard` | GET | 是 | 登录 + 有店 |
| `/shops`、`/shops/{id}/products` | GET | 否（用户端，免登录） | — |
| `/redeem`、`/my-redemptions` | POST/GET | 否（用户端） | 登录 |

即：**商家专用 9 个，用户端 4 个**，共用一个前缀，靠字面量段区分。

### 2. 商家身份如何识别

`JWT → get_current_user_id() → merchant.user_id 反查`。`user` 表**没有 role 字段**（41 列里只有 `status`），身份全靠 `merchant.user_id` 反向关联，且 `uk_merchant_user` 唯一索引保证**一账号一店**。

两个必须注意的实测事实：
- **未入驻不是 404**：`GET /merchant/info` 未入驻时返回 `200 {merchant: null, enabled: true}`（后端刻意这么设计，让前端用同一个接口决定渲染表单还是工作台）。
- **两套 token 不通用**：管理端是 `admin` 表 + `type=admin` 的 token，走 `/api/admin`；商家走用户侧 JWT。商家**没有任何管理端权限**（审核与结算在管理后台）。

### 3. 未入驻 / 待审核 / 已通过（含已拒绝、已停业）五种状态的处理方案

| `merchant.status` | 守卫动作 | 页面表现 |
|---|---|---|
| `null`（无店） | 放行到 `/merchant/apply` | 入驻表单 |
| `0` 待审核 | 重定向 `/merchant/apply` | **状态视图**：⏳ 审核中 + 提交时间 + "修改资料重提"按钮 |
| `1` 已通过 | 放行工作台 | 4 个页面正常 |
| `2` 已拒绝 | 重定向 `/merchant/apply` | **状态视图**：红框显示 `audit_reason` 拒绝原因 + "重新申请"（表单预填原值） |
| `3` 已停业 | 重定向 `/merchant/apply` | 状态视图：已停业说明（后端不允许重提，按钮置灰） |

**关键取舍：不做单独的"审核中提示页"**。任务书第 1 节本来就要求 Apply 页"如果已提交过 → 显示当前状态"，所以状态视图放在 `Apply.vue` 内部（同一个文件 4 个分支），守卫只做"非 visitor 状态一律送 Apply"这一件事——少一个页面、少一套样式，且状态与表单天然共享同一份 `merchant.info`。

### 4. 独立 Layout 的设计方案

任务书写的是"侧边栏 + `<router-view />`"的嵌套布局。**本项目不改造成嵌套路由**，理由 + 方案如下：

- 现状是**平铺路由**，父级 `/merchant` 已被 `MerchantList`（积分商城首页，必须留在 MainLayout 里带导航）占用。若把 `/merchant` 改成带 children 的父路由，用户端商城首页就没法同时存在，需要把路径迁到 `/merchant/shop` —— **会动到阶段二已验证的路由与导航**。
- 项目已有成熟范式：**平铺路由 + 子页内部以 Layout 为模板根**（`ProfileSubLayout` 就是这么用的，11 个子页全部如此）。
- 因此：`MerchantLayout.vue` 只做「顶栏 + 侧边栏 + `<slot />`」，4 个工作台页面各自把它当模板根（`<MerchantLayout><section>…</section></MerchantLayout>`）。**不做嵌套、不动 `/merchant` 与 `/merchant/:id`**。

配套需要两处改动：

1. `App.vue` 加一个 layout 开关：

```vue
<el-config-provider :locale="zhCn">
  <RouterView v-if="isBareLayout" />
  <MainLayout v-else />
</el-config-provider>
```
```js
const route = useRoute()
// 商家工作台自带顶栏与侧边栏，不能再套 AppNav/footer/悬浮按钮
const isBareLayout = computed(() => route.meta.layout === 'merchant')
```

2. `MerchantLayout` 自己补 `userStore.hydrate()`（MainLayout 不再挂载，否则**直链刷新 `/merchant/dashboard` 时助老/高对比度类名不会挂到 `<html>` 上**，主题失效）。`hydrate()` 幂等且读本地缓存，代价可忽略。

另外工作台根元素用 `<div class="mw-shell">` 而非 `<main>`：`global.css` 里 `main { width: min(1180px, 88vw) }` 会把"侧边栏 + 内容区"整体压窄，工作台自带宽度更合适。并在顶栏保留一个「返回积分商城」出口（绕开 MainLayout 后就没有"返回首页"悬浮键了，不能留死胡同）。

## 五、页面设计要点（含已识别的真实坑）

### 5.1 布局切换
见第三节第 4 问。补充：bare 模式下 `profileStore.rootClasses` 不再随 `.app-shell` 绑定，但 `syncDom()` 仍在 `html` 上挂类，全局主题照旧生效；`MerchantLayout` 再绑一次 `rootClasses` 到自己的根元素，保证组件级 scoped 样式也能命中。

### 5.2 路由与守卫

```
/merchant/apply      layout=merchant, requiresAuth              → Apply.vue
/merchant/dashboard  layout=merchant, requiresAuth, mch          → Dashboard.vue
/merchant/products   layout=merchant, requiresAuth, mch          → Products.vue
/merchant/verify     layout=merchant, requiresAuth, mch          → Verify.vue
/merchant/settings   layout=merchant, requiresAuth, mch          → Settings.vue
```
（`mch` = 守卫里校验商家状态；`/merchant/apply` 不校验，否则未入驻会被自己重定向成死循环）

守卫实现要点：
1. **未登录优先判**：`requiresAuth && !localStorage.getItem('token')` → 直接跳 `/login?redirect=…`，**不发请求**（否则会先 401 再被拦截器 `window.location.href` 硬跳，丢 redirect）。
2. **身份信息走 store 缓存**：`useMerchantStore().fetchInfo()` 内部缓存，命中即同步返回；导航只在 `reset()`（退出登录）后失效。否则每次跳转都打一次 `/merchant/info`。
3. **守卫返回值而非 `next()`**（与现有守卫风格一致）：`{ path: '/merchant/apply' }`。
4. **失败不静默**：`/merchant/info` 请求异常（网络/500）不当作"未入驻"，而是放行到 Apply 页并显示"身份校验失败，请重试"——避免把商家误判成访客、白丢一次入驻申请。

### 5.3 Apply.vue（4 态）
- 表单：店铺名（必填）、店铺类型（下拉，**值取真实库实际分类**：打印/便利店/理发/回收/家政）、联系方式、地址、店铺简介。
- 提交：`POST /merchant/apply`；成功后 `merchantStore.fetchInfo(true)` 刷新 → 自动切到"审核中"视图。
- **重提的既有陷阱（阶段一已修，前端要配合）**：后端改为"只覆盖显式传入字段"，所以重提时**不能只传 name**——本页重提时把表单里所有字段（含空串）都显式传出去，用户清空的项要真的被清空。
- 已通过状态进来：显示"您已入驻" + 直接跳工作台按钮（后端 `POST /apply` 会 400"您已入驻，无需重复申请"，不做这个分支用户会撞错误弹框）。

### 5.4 Dashboard.vue
- 4 张卡：今日核销 / 累计核销 / 服务用户 / 待核销订单（第 4 张来自 `/redemptions?status=1&size=1` 的 `total`）。
- 热门商品 Top5：进度条式列表（`sold_count` 相对最大值做宽度百分比）。
- 7 天趋势：**纯 CSS 柱状图**——`height: (count/max)*100%`，`max=0` 时全部给 2px 兜底高度（否则整排柱子消失），柱顶标数值、`aria-label` 补读屏文本。
- 两个请求并发（`Promise.allSettled`），任一失败只让对应区块显示重试，不整页空白。

### 5.5 Products.vue
- 列表形态建议用 **CSS Grid 行**（列：图 / 标题 / 积分 / 库存 / 已兑换 / 状态 / 操作），窄屏自动堆叠。
  不用 `el-table`：项目里 11 个列表页（FavoritesView/ExchangesView/RedemptionsView…）全是自定义行，`el-table` 在高对比度与助老模式下的覆盖成本高、且与现有视觉不一致。
- 新建/编辑 Dialog：`el-dialog` + 复用 `ImageUploader`（`v-model` 拿 `File`）+ 积分 0 时提示"免费券"（与阶段二同一套文案口径）。
- **Dialog 内请求带 `skipErrorToast`**，错误在 Dialog 内提示。
- 下架：二次确认 → `PUT /products/{id}/offline`；**上架按钮依赖 B2**，无 B2 则置灰并注明"如需重新上架请联系平台"。
- 库存为 0 的商品给"已兑完"角标（后端 `redeem` 会因 `stock>0` 条件更新失败而拒单）。

### 5.6 Verify.vue（核心页）
- 输入区：
  - 原生 `<input>`（非 `el-input`），`inputmode="numeric"`、`autocomplete="off"`，**大字 32px+**、字距放大、居中。
  - 分组显示 `123 456`：受控输入 + `nextTick` 光标归位到末尾（`el-input` 做不到这种格式化，会被光标跳位反噬）。
  - `input` 时 `.replace(/\D/g,'').slice(0,6)`；**全程字符串，绝不 `Number()`**（阶段二已实测：`012345` 会被显示成 `12 345`）。
  - 满 6 位自动提交；提交期间 `submitting` 红旗锁 + 输入框禁改，**杜绝连点双提交**（后端虽然有条件更新兜底，但前端不该造重复请求）。
  - 支持粘贴（`paste` 事件剥非数字）与扫码枪（本质是快速输入 + Enter）。
- 结果区：成功 → 大绿勾 + 商品 / 用户 / 核销时间 + [继续核销]（清空、聚焦、刷新历史）；失败 → 大红叉 + 后端中文原因（`404 核销码不存在` / `400 已使用，请勿重复核销` / `400 已过期` / `403 该核销码不属于本店`），四种文案直接透出，不再自造。
- 历史区：`GET /redemptions?status=2&size=10`，核销成功后自动刷新。

### 5.7 Settings.vue

## 六、状态类名方案（第四套 `ms-*`）

项目已有三套状态类名：`s-*`（物品/需求，`Profile.vue`）、`os-*`（交换单，`Profile.vue`）、`rs-*`（兑换单，阶段二 `rs-pending/rs-redeemed/rs-expired/rs-cancelled`）。本批新增**第四套 `ms-*`**，三组不重名、不串用：

| 对象 | 类名 | 语义 |
|---|---|---|
| 店铺状态 | `ms-pending` / `ms-approved` / `ms-rejected` / `ms-closed` | 待审核 / 已通过 / 已拒绝 / 已停业 |
| 商品状态 | `ms-online` / `ms-offline` | 上架 / 下架 |
| 商家侧兑换单 | `ms-redeem-wait` / `ms-redeem-done` / `ms-redeem-expired` / `ms-redeem-cancelled` | 待核销 / 已核销 / 已过期 / 已取消 |

两个设计理由：
1. **商家侧兑换单不复用 `rs-*`**：按你的硬约束不串用；且商家侧用「小圆点 + 文字」（低饱和、信息密度高）与用户侧 `rs-*` 的实心胶囊在视觉上区分，一眼看出是"工作台视角"。
2. **语义命名而非数字命名**：`s-1`/`os-2`/`rs-3` 那种数字类名在跨文件复用时极易错位（阶段二就踩过"已核销显示成灰色"），商家侧一律语义化。

## 七、冲突与风险排查（13 条）

| # | 风险 | 实测/结论 |
|---|---|---|
| 1 | `/merchant/apply|dashboard|products|verify|settings` 与既有 `/merchant/:id` 通配段冲突 | **无冲突**。用真实 `vue-router` 解析实测：静态段全部命中静态路由，`/merchant/1` 仍命中 `detail`，`/merchant/nonexistent` 落回 `detail`（走 404 分支，符合预期）。vue-router 4 按 score 排序，与声明顺序无关 |

| 7 | 导航已 8 项，再加会挤 | **不加导航项**，改走页面内入口（D3） |

| 9 | 下架不可逆 | 见第四节 B2 / D1 |

| 12 | 双弹（拦截器 + 页面） | verify / 商品增改 / 兑换类请求一律 `skipErrorToast` |
| 13 | 高对比度下 emoji 占位块在黑底上隐形 | 与阶段二同法：占位块加 `border: 1px solid #fff`（阶段二已实测过该问题） |
