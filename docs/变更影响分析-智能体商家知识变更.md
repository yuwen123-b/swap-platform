## 0. 一句话结论

根因**两条都成立**（提示词无平台概览 + 无商家工具），但**任务书里有 1 处事实性错误会直接导致 AI 教用户撒谎**：

> ⚠️ 任务书 FAQ 模板写「把书发布到平台（**选'换积分'或'交换'**）」——**「换积分」这个选项在前端和后端都不存在**（发布弹窗只有「免费送 / 交换 / 低价转让」三项，后端 `EXCHANGE_MODES = (1, 2, 3)` 硬校验）。照抄会把「AI 不知道商家模块」修成「AI 编造一个不存在的按钮」，比现在更糟。

其余结论：**改动集中在 1 个文件（`app/services/agent.py`） + 3 个新文件**，零 DB 变更、零接口变更、零新依赖、零前端改动。

### 1.2 助手提示词现状（`agent.py:14-27`）

`SYSTEM_PROMPT` 现有内容只描述**角色与输出约束**，**完全没有平台功能描述**：

- 「你是『社区旧物互换平台』的智能助手『邻里通』」（`agent_name = 邻里通`）
- 定位「社区百事通式工具型助手：专业、简洁、可信」
- 5 条输出约束：① 基于工具真实数据不编造 ② **不主动推荐用户做别的操作** ③ 问附近物品必须先调工具 ④ 工具失败如实说 ⑤ 无关问题引导回平台话题
- 一段**禁止话术黑名单**：`'建议您打开平台首页...'` / `'可以上传自己的闲置物品...'` / `'交换成功后记得在平台确认完成...'` / `'可以获得积分奖励哦~'`

> 🔴 **这正是报告里那句「我这边没有平台『商家服务』兑换规则的数据」的直接来源**：提示词里除了「社区旧物互换平台」七个字，对平台能干什么一个字都没写，模型只能承认自己不知道。**证据：`grep -rni "merchant" app/services/agent.py app/agents/` → 0 命中。**

### 1.3 工具注册机制：三层结构（没有统一注册表）

```
① 触发层   _is_xxx_request(question)        ← 关键词命中判定（agent.py）
② 契约层   _XXX_TOOL = {OpenAI schema}       ← 内联 dict（agent.py）
③ 分发层   _call_xxx_tool(name, args)        ← 路由到服务层（agent.py → services/）
```

路由优先级（`agent.py:450-516` `stream_tokens`）：

| 优先级 | 分支 | 触发条件 | 工具 |
|---|---|---|---|
| 1 | 物品查询 | `_is_item_query_request`（"想换/求购/有没有/附近有/闲置/二手"…） | `search_items`、`find_nearby_items`（+ 可选 `maps_geo`） |
| 2 | 高德地图 | `mcp_client.is_amap_configured()` 且 `_is_amap_request` | amap MCP 全套 |
| 3 | 图表 | `mcp_client.is_configured()` 且 `_is_chart_request` | `generate_chart` |
| 4 | 普通对话 | 兜底 | 无工具 |

关键机制：每层都是「**非流式 `chat_with_tools` 决策 → 执行工具 → 结果以 `role=tool` 回填 → 第二轮 `chat_stream` 流式产出**」两轮式；任一层抛异常则**降级到下一层**，保证对话不中断（`agent.py:460-497`）。

> ✅ 结论：任务书第三步「让 LLM 调用工具」所需的一切机制**都已具备**，只需按同一范式接线。

## 5. 方案设计

### 5.1 提示词分层（关键设计：**追加而非改写**）

```
BASE_SYSTEM_PROMPT
  = SYSTEM_PROMPT                ← 原文一字不改（语气 + 5 条约束 + 禁语黑名单）
  + PLATFORM_OVERVIEW            ← 【新增】平台功能概览（任务书第一步的内容）
  + POINTS_RULES_BLOCK           ← 【新增】积分规则动态块（可选，见 D2）
```

`BASE_SYSTEM_PROMPT` 替换掉现有 4 处的 `SYSTEM_PROMPT + ...`（`agent.py:135 / 356 / 410 / 501`）→ **4 个分支全部获得平台知识**（不只是商家分支）。这一步是修 bug 的**主要贡献者**：用例 1、用例 3 都是「知识问答」，靠它解决，不靠工具。

`PLATFORM_OVERVIEW` 内容结构（任务书给了草稿，我按事实修正后落地）：

```
【平台概览】平台名称「闲物焕新」，社区旧物互换 + 积分兑换平台，智能助手叫「邻里通」。
【核心功能】1 探索物品「闲」：邻里之间交换/转让/免费送二手物品
            2 探索物品「新」：用积分兑换商家商品（商家好物）
            3 发布物品：上传闲置 → 平台审核 → 通过后 +10 积分
            4 完成交换：双方各 +20 积分、各 +5kg 碳减排
            5 积分商城：用积分兑换社区商家商品
            6 商家核销：兑换后拿到 6 位核销码，到实体店出示核销
            7 碳积分：累计环保贡献（碳减排量与积分是两套口径，不可互相换算）
【积分规则】发布物品 +10（审核通过时，不是发布时）
            完成交换 +20（买卖双方各一次）
            积分商城兑换按商品标价扣分
            100 积分 = 1 元（平台与商家结算口径，面向用户时不需主动提及）
【社区商家】5 家，覆盖 打印 / 便利店 / 理发 / 回收 / 家政 五类
            例如：社区打印店「打印券10张」50 分、24小时便利店「纸巾1包」30 分、
                 美发工作室「基础理发券」200 分（实时名单与价格以工具查询为准）
【兑换流程】积分商城 → 选商品 → 确认兑换 → 获得 6 位核销码 → 到店出示核销码核销
【常见问答口径】（见 §5.5，含与禁语黑名单的协调说明）
```

### 5.2 工具链路由：**推荐「并入现有物品分支」而非「新开独立分支」**

任务书的第三步默认「新开一个商家分支」。读代码后我认为**并入更优**，两种方案对比：

| | 方案 A：并入现有第 1 层分支（**推荐**） | 方案 B：新开独立商家分支 |
|---|---|---|
| 改动 | 把 3 个商家工具**加入** `_stream_item_query_response` 的工具列表；把商家关键词**加入** `_ITEM_QUERY_KEYWORDS`；指令追加；分发函数扩 1 个 `if` | 新增一组关键词判定 + 新增 `_stream_merchant_response`（与物品分支近乎重复的 60 行） |
| 代码量 | 约 +15 行 | 约 +90 行 |
| 排序风险 | **无**（一个分支，LLM 自选工具） | **有**：必须决定插在物品分支前/后。「附近有没有打印店」含 `附近有没有`（物品关键词）→ 若商家分支在后就被物品分支抢走；若在前，则「兑换一本教材」这类含「兑换」的物品问题会被商家分支抢走 —— **两难** |
| 关键词重叠 | 无冲突（同一分支，关键词取并集） | 需要精心调关键词集合，互相抢 |
| 模型选择 | LLM 在 5 个候选工具里选（描述清晰即可） | LLM 只在 3 个工具里选，但**前提是路由判断对了** |
| 单轮往返 | 1 次 | 1 次 |

**方案 A 的关键收益**：修好后「有哪些商家」和「附近有没有打印店」**走同一条链**，由 LLM 依据工具描述决定调 `get_merchant_list` 还是 `search_items`，从根上消除关键词抢单问题。

方案 A 的代价：第 1 层分支的 system prompt 变长（≈ +700 字）、工具数从 3 变 6。对 token 与模型判断力的影响可忽略。

### 5.3 三个工具的契约

| 工具 | 参数 | 返回（给 LLM 的 JSON） |
|---|---|---|
| `get_merchant_list` | `category`(可选，打印/便利店/理发/回收/家政) | `[{merchant_id, name, category, address, contact, description, product_count}]` |
| `get_merchant_products` | `merchant_id`(必填)、`keyword`(可选) | `{merchant:{...}, products:[{product_id, title, points_cost, stock, sold_count, is_free}]}`；商家不存在/未通过 → `{error: "商家不存在或暂未开放"}` |
| `get_points_balance` | 无（user_id 由服务端注入） | `{points, level, level_label, carbon_total, exchange_count, next_level, next_level_gap}`；未登录 → `{error: "未登录"}` |

**设计要点**：
- 全部**只读**，与 `item_query_service` 同风格（不写库、不抛异常给 LLM、失败返回 `{"error": ...}` 让 LLM 措辞）
- **`user_id` 由 `viewer_user_id` 注入，不让 LLM 传**（与 `find_nearby_items` 的隐私处理同思路）——避免模型编造 user_id 查别人的积分
- 返回**只带 LLM 需要的最小字段**，避免把 `logo_url` 签名 URL、`audit_reason` 等噪音塞进上下文
- 商品 `points_cost = 0` 显式给 `is_free: true`（沿用「免费券」文案口径，与阶段三商家端一致）

### 5.4 关键词扩展（方案 A）

`_ITEM_QUERY_KEYWORDS` 追加（**不改动原有条目**）：


### 5.5 FAQ 口径与「禁语黑名单」的协调（**必须做，否则自相矛盾**）

现有 `SYSTEM_PROMPT` 硬约束：**「不要主动推荐用户去做别的操作（如'打开平台首页'、'上传闲置物品'、'确认交换完成'、'获得积分奖励'）」**，并明确把 `'可以上传自己的闲置物品...'`、`'可以获得积分奖励哦~'` 列为**禁止话术**。

而任务书要加的 FAQ 模板恰好是这类话术（「您可以先把书发布到平台…审核通过后 +10 积分…」）。

**冲突是真的**：不加协调语句，模型要么因为禁语约束**拒绝回答**（等于没修），要么在**所有**回答后面都挂一句「建议您去积分商城看看」（回归到敷衍话术）。

**协调方案**（写进 `PLATFORM_OVERVIEW` 末尾，只加 1 句）：

> 「以上流程说明**仅在用户主动询问**兑换 / 积分 / 商家相关问题时使用，例如用户问『怎么兑换』『积分怎么用』『有哪些商家』。
> 用户问其他问题时（如找物品、问附近），**仍然遵守既有的『不主动推荐操作』约束**，不要附加任何积分或兑换建议。」

改动位置：新增内容里，**不动原 `SYSTEM_PROMPT` 一个字** → 既有约束不被削弱，新话术被明确圈定范围。
