# 变更影响分析：商家端闭环 · 前端用户侧

- 版本：2026-10-15
- 阶段：第二阶段（前端）中的**用户侧**部分
- 范围：`积分商城` 商家列表 → 商家详情 → 兑换 → 核销码 → 我的兑换；**不含**商家工作台、不含管理端审核/结算页
- 前置：阶段一已完成（后端 5 张表 + 20 个接口；4 家种子商家/10 个商品已在真实库）
- 结论：**可行性无阻塞**，但有 **13 处与任务书不一致或需要定口径**的地方，其中 5 处会直接导致页面渲染错误，必须先定。

## 0. 结论摘要（先看这个）

|---|---|
| 任务书要求的技术方案 | 全部可行，**零新依赖**（前端 package.json 不需要加任何包） |

## 1. 必读文件核查结果

### 1.1 导航栏现有结构（`src/components/AppNav.vue`）

**7 个入口**，由一个 `NAV_LINKS` 常量数组驱动（第 37–45 行），模板 `v-for` 渲染，新增一项只需追加数组元素：

```
· 智能体助手 /assistant · 我的私信 /messages · 个人中心 /profile
```

样式由 `global.css` 的 `nav.topnav` 提供（第 166–199 行），`AppNav.vue` 自身的 `<style scoped>` 是**空的**（只有一行注释）。响应式断点已存在：

| 断点 | 表现 |
|---|---|
| > 1100px | 正常横排，`gap: 30px` |

## 2. 导航栏入口该加在哪里

**建议：插在 `探索物品` 之后，作为第 2 项。**

```js
const NAV_LINKS = [
  { path: '/items', label: '探索物品' },
  { path: '/merchant', label: '积分商城' },   // ← 新增
  { path: '/recognition', label: '物品识别' },
  ...
]
```

理由：

1. 「探索物品」和「积分商城」是**同类入口**（都是"去逛逛"），放一起符合用户心智；放末尾会让"逛"和"设置"混在一起。
2. `RouterLink` 自动加 `router-link-active`，`/merchant` 与 `/merchant/:id` 都会高亮（Vue Router 4 的前缀匹配，符合预期）。
3. **不推荐**放进 `SETTING_TILES`：那是"设置"语义，且磁贴样式（`tile-icon` 40px emoji）不适合承载入口价值最高的功能。

**副作用**：导航从 7 项变 8 项。≤900px 会多折一行。这是可接受的（现网已有 wrap 机制），且**不改 `global.css` 的 nav 样式**（避免影响其他页面）。

## 3. 页面与组件拆分方案

### 3.1 组件树

```
AppNav.vue  ─── +1 NAV_LINKS 项
│
├─ /merchant          MerchantList.vue          【新建·页面外壳】
│    ├─ 头部：标题 + 副标题 + 积分为止卡片（未登录→登录引导）
│    ├─ 分类 chips（常量 5 类 + 全部，本地内联，不抽组件）
│    └─ 商家卡片 × N（本地内联，v-for；点击 → /merchant/:id）
│
├─ /merchant/:id      MerchantDetail.vue        【新建·页面外壳】
│    ├─ 返回栏（← 返回积分商城）
│    ├─ 店铺信息卡（logo 占位 / 名称 / 分类 / 地址 / 联系电话 / 简介）
│    ├─ 可兑换商品列表 × N（本地内联 mini-row 风格）
│    └─ <RedeemConfirmDialog>  ← 点「立即兑换」拉起
│
├─ /profile/redemptions   profile/RedemptionsView.vue   【新建·ProfileSubLayout 作根】
│    ├─ Tab：全部 / 待核销 / 已核销 / 已过期
│    ├─ 兑换记录行 × N（本地内联）
│    ├─ 分页
│    └─ <RedeemCodeDialog>   ← 点某条记录拉起（放大展示核销码）
│
└─ Profile.vue  ─── +第 7 区「我的兑换」mini 卡（最近 3 条待核销 → 查看全部）
```

### 3.2 两个共享组件（抽出来的唯一理由：被多处复用）

**A. `src/components/RedeemConfirmDialog.vue`** —— 兑换确认 + 成功后直接切到核销码

| 项 | 内容 |
|---|---|
| props | `modelValue`(Boolean)、`product`(Object)、`merchantName`(String)、`points`(Number，当前余额) |
| emits | `update:modelValue`、`success`(payload=redeem 返回体) |
| 内部状态 | `submitting`（防连点）、`result`（拿到后切换到核销码视图） |
| 关键文案 | 「消耗积分 50 分」「当前积分 245 分 → 剩余 195 分」「有效期 30 天」 |
| 特判 | `points_cost === 0` 时文案改为「免费兑换券 · 不消耗积分」，剩余积分不变（见 D5） |
| 请求 | `redeemProduct()` 必须带 `skipErrorToast: true`（D10） |
| 成功后 | 内部渲染核销码大字视图（不关窗），底部两个按钮：`查看我的兑换` → `/profile/redemptions`、`完成` → 关窗 |
| 关闭后 | emit `success`，父页面刷新积分 + 商品库存 |

**B. `src/components/RedeemCodeDialog.vue`** —— 纯展示核销码（我的兑换页复用）

| 项 | 内容 |
|---|---|
| props | `modelValue`、`code`、`expiresAt`、`productTitle`、`merchantName`、`status` |
| 展示 | `✓ 兑换成功` / 核销码 `123 456`（3+3 空格格式化，字号 clamp(36px, 8vw, 56px)）/ 「向商家出示此码完成核销」/ 「有效期至 2026-11-14」/ 已核销的单显示 `已于 x 核销` |
| 按钮 | `查看我的兑换`（可选，传入时显示）+ `完成` |

> 为什么拆两个而不是一个双态弹窗：核销码展示要**独立**出现在「我的兑换」页（那里没有"确认兑换"这一步）。如果合成一个，我的兑换页就得传一个假 `product` 进来——典型的为复用而耦合。

### 3.3 页面级细节

**MerchantList.vue**

- 外壳：`<section class="page merchant-page">`，`max-width: 820px`（与 Profile 一致，卡片列表不需要 1180px 宽）
- 顶部积分条：**未登录不显示数字**，改为「登录后可查看积分并兑换」+ 登录按钮（见 D2）
- 分类 chips：`['全部','打印','便利店','理发','回收','家政']`，切 chips → `getMerchantList({ category, page:1, size:50 })`
- 商家卡片（按任务书布局，但**去掉距离**，见 D1）：
  ```
  ┌──────────────────────────────────────────┐
  │ [🖨️占位] 社区打印店                    →  │
  │           打印 · 在售 2 项                 │
  │           小区北门 1 号楼底商              │
  │                              打印券10张 50积分起 │
  ```

- 最低价：卡片右下角「`<最低价商品名>` `N` 积分起」需要**再调一次** `/shops/{id}/products` 才能拿到——5 家店就是 5 个额外请求。

  **我的方案**：列表接口不返回最低价 → **卡片不显示"XX积分起"**，改为显示 `在售 N 项`，把"多少钱"留给详情页。理由：为了一行装饰文案引入 N+1 请求不值当，且 `/shops` 已经返回 `product_count`，免费拿到。
- 空态：「暂无商家，敬请期待」+ `🌿`（复用 `green-empty` 视觉语言）
- 加载中：`v-loading`

**MerchantDetail.vue**

**Profile.vue 第 7 区**

### 3.4 `src/api/merchant.js`

```js
import request from './request'

// ===== 用户端（4 个）=====
export const getMerchantList = (params) => request.get('/merchant/shops', { params })
// 语义别名：任务书要求的 getMerchantDetail —— 注意它返回 { merchant, list }，不是数组
export const getShopProducts = (id) => request.get(`/merchant/shops/${id}/products`)
export const getMerchantDetail = (id) => getShopProducts(id)
// Dialog 内自定义错误提示 → 必须静默拦截器的统一 toast
export const redeemProduct = (productId) =>
  request.post('/merchant/redeem', { product_id: productId }, { skipErrorToast: true })
export const getMyRedemptions = (params) => request.get('/merchant/my-redemptions', { params })
```

> `baseURL = /api/v1`，所以响应外壳的 `code === 0` 判定（`request.js` 第 8 行）对用户侧接口成立。**商家端 9 个接口本批不封装**（不做商家工作台），避免无用代码。

## 5. 潜在冲突逐条排查

| # | 位置 | 冲突 | 结论 |
|---|---|---|---|
| 1 | 路由 `/merchant` | 与后端 `/api/v1/merchant` | **无冲突**。vite dev 只 proxy `/api`（`vite.config.js` 第 8 行），`/merchant` 不被代理；生产端由 history fallback 交给 SPA。 |

| 4 | api 文件 | `api/merchant.js` 与 `api/item.js`/`order.js` 无重名 | **无冲突** |

## 7. 无障碍与主题实现要点（约束的落地方式）

1. **三件套必须齐**：每个新页面/组件都要有 ① `:focus-visible` 3px 焦点环 ② 语义标签（`role="tablist"`/`role="tab"`/`aria-selected`）③ 非 scoped 的 `html.mode-elderly` / `html.theme-high-contrast` 覆盖段。
2. **助老模式按钮 ≥60px**：`ProfileSubLayout` 的 `html.mode-elderly .sub-page .el-button { min-height: 60px }`（第 283 行）对「我的兑换」页**自动生效**；`MerchantList` / `MerchantDetail` 不在 `.sub-page` 下，必须在自己的非 scoped 段写 `html.mode-elderly .merchant-page .el-button { min-height: 60px; font-size: 18px }`。商家卡片是 `<button>` 不是 `el-button`，要单独加 `min-height: 72px`。
3. **高对比度**：卡片色板改为
   ```css
   html.theme-high-contrast .merchant-page { --mp-card: #000; --mp-border: #fff; --mp-text: #fff; --mp-text-sub: #f2f2f2; }
   ```
   `rs-*` 在高对比度下改为**浅底黑字**（照抄 ExchangesView 的 `os-*` 处理，第 760–788 行）。
4. **占位块在高对比度下**：`--pc-bg` 在主题里会变黑 → 占位块必须**加 1px 白描边**，否则整块隐形。
5. **核销码可读性**：`aria-label` 用「核销码 4 8 2 9 1 3」逐位读出（视障模式），视觉上用 3+3 空格分组。
