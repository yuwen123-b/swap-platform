- **无任何 merchant 相关条目。**

**渲染机制**（模板第 9–23 行 + 第 97–106 行）：

```js
const visibleMenus = computed(() =>
  menus
    .filter((m) => m.roles.includes(store.role))              // 一级按 role 过滤
    .map((m) => m.children
      ? { ...m, children: m.children.filter((c) => c.roles.includes(store.role)) }
      : m)                                                     // 二级同步过滤
    .filter((m) => !m.children || m.children.length > 0),      // 组内全空 → 整组隐藏
)
```

模板两种形态：有 `children` → `el-sub-menu`（`child.path` 直给 `el-menu` 用，**必须是绝对路径**）；无 `children` → `el-menu-item`。

→ **新增「商家管理」只需往 `menus` 数组插一个带 `children` 的对象，模板一行都不用改。**

## 7. 阻断项 D1（唯一真正卡住实现的点）

**结算页给不出正确的「本期待结算单数 / 佣金金额」。**

事实链：
1. `settle_merchant` 的真实口径 = **该商家 + 当月 + `redeemed_at` 落在区间 + `status=2`**；
2. `/merchant/list` 返回的 `redemption_count` = **累计**（无时间范围）→ 跨月场景下**偏大**；
3. 积分总额与汇率**任何接口都不返回** → 前端无法自算佣金；
4. 结算**幂等**（已结算的调了不重写），按钮看起来仍可点 → 会承诺「将结算 N 单」实际 0 单。

→ 对**不可逆操作**（结算）给出错误承诺，是本模块最大的风险点。

**三个方案（需你选一个）**：

| 方案 | 做法 | 代价 | 弹窗数字 |
|---|---|---|---|
| **A（推荐）** | 后端 **+1 个只读接口** `GET /api/admin/merchant/settlements/preview?period=YYYY-MM`，按 `settle_merchant` 同一口径返回每个已通过商家的 `{merchant_id, name, redemption_count, points_total, commission_amount, settled, settled_at}`。~40 行，复用 `parse_period` + `calculate_commission`，**零副作用** | 破「后端 0 改动」约束 | ✅ 100% 准确，且能永久禁用「本期已结算」的行 |
| **B** | 守住 0 改动：结算页只做「历史记录 + 触发结算」，**弹窗不带 N/¥**，改为「即将为「X 店」结算 2026-10 周期，操作不可撤销」；per-merchant 列表「核销单数」用累计口径**并把列名如实改成「累计核销」** | 不满足任务书「弹窗显示 N 单/¥X」原文 | ⚠️ 无数字 |
| **C** | 0 改动 + 前端硬编码 `0.01` 估算 | 汇率写死前端（配置漂移）；积分总额仍需逐商家分页拉完所有兑换单求和（N 次请求），且仍非当期口径 | ❌ 会失真，**不推荐** |
