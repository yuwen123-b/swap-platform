# 移动端（H5）适配影响分析

> 目标：在**不破坏 PC 宽屏展示**的前提下，让 `agent_front` 在 375–430px 的手机浏览器（微信内置 / Safari / Chrome 移动端）可用。
> 本文所有结论均来自代码实查（含行号），不是推测。

---

## 一、现状核查：任务书的 5 处假设与代码不符

先把"以为要改"和"实际要改"分清楚，避免无谓改动破坏现有布局。

| # | 任务书假设 | 代码实况 | 结论 |
|---|---|---|---|
| 1 | 缺 viewport | `index.html` **已有** `<meta name="viewport" content="width=device-width, initial-scale=1.0">` | ✅ 不用加，只需补 `viewport-fit=cover`（iPhone 刘海安全区） |
| 2 | 列表页 4 列需改 1–2 列 | `ItemList.vue:62-102` 用的是 `el-col :xs="12" :sm="12" :md="8" :lg="6"` → **手机本来就是 2 列**；`MerchantList` 的 `.shop-list` 是 `flex-direction: column` → **本来就是单列** | ⚠️ 不用"从 4 改 1"，只要在 <420px 把 `xs` 降到 24（单列）避免挤压 |
| 3 | `el-table` 需横向滚动 | 用户端 **零 `el-table`**（`grep -rn "el-table" src/` 无结果），表格只在管理端 | ✅ 该条**不适用**，无需处理 |
| 4 | 3D/360 需"检查是否开启 touch" | `ModelViewer.vue:205` 用 `OrbitControls`（双指缩放原生支持）；`:334` 已写 `touch-action: none`。`PanoramaViewer.vue:11-14` 用 pointer events + `:397` `touch-action:none` + `setPointerCapture` | ✅ **单指旋转两端都已可用**；❌ 但 `PanoramaViewer` **确实没有双指缩放**（全站都没有，PC 上连滚轮缩放都没有）→ 需补 |
| 5 | 各页需逐个改网格 | `ItemDetail:1210`、`Pricing:550`、`Message:443`、`Review:354`、`Recognition:209` **已有** ≤700 单列折叠；`Home:1409` 已有 900px 断点 | ✅ 大部分已就绪，只需补细节 |

**一句话结论**：这不是"从零适配"，而是**补 4 类真缺口 + 统一一层移动端外壳**。

## 二、真正的缺口（按严重度排序）

| 严重度 | 缺口 | 证据 | 手机上会怎样 |
|---|---|---|---|
| 🔴 P0 | **没有移动端导航** | `AppNav.vue:59-67` 7 项文字导航；`global.css:526` 只在 ≤800 时 `flex-wrap: wrap` + 横向滚动 | 7 项挤成两行横滚，占掉 1/3 首屏，且滚动条藏入口 |
| 🔴 P0 | **`main` 宽度与内边距双杀** | `global.css:274` `width: min(1180px, 88vw)`；`global.css:538` ≤800 时 `min(90vw, 600px)`；`.page` `padding: 64px 0` | 375px 屏上正文只有 **337px** 宽，两侧再被卡片的 padding 吃掉，显得又窄又挤 |
| 🟠 P1 | **Assistant 用 `100vh` 算高度** | `Assistant.vue:89` `height: calc(100vh - 108px)` | 微信/Safari 地址栏伸缩 → 输入框被顶出屏幕；键盘弹起后输入框被遮 |
| 🟠 P1 | **弹窗未适配** | 11 个文件用 `el-dialog`，全局只有助老/高对比两处覆盖（`global.css:627/748`），无尺寸规则 | 默认 `width: 50%` → 375px 上只有 187px，内容全挤成一列 |
| 🟠 P1 | **表单 label 左对齐** | Element Plus 默认 `label-width` 横向排布 | 手机上一行只剩 150px 输内容，"名称""成色"就被挤成两行 |
| 🟡 P2 | **悬浮按钮与底部 Tab 冲突** | `MainLayout.vue:61/92` `.voice-fab` 与 `.back-home` 都 `bottom: 30px` | 加底栏后会互相压住 |
| 🟡 P2 | **无横向溢出兜底** | `body` 无 `overflow-x` 规则 | 任何一个超宽子元素都会让整页能左右拖，微信里表现为"页面晃动" |
| 🟡 P2 | **360° 无缩放** | `PanoramaViewer` 无 wheel / 无双指逻辑 | 手机上看不清细节，也无法放大 |
| ⚪ P3 | **构建未声明移动端 target / base 写死** | `vite.config.js` 无 `base`、无 `build.target` | 部署到子目录时资源 404；老 iOS 可能不认部分语法 |

## 四、断点策略（为什么不新造一套）

现有断点分布：`480×7 / 560×4 / 700×1 / 750×2 / 768×1 / 800×4 / 860×1 / 900×5`。

**不统一重构**（那是破坏性变更），只做两件事：

1. 新增一个**唯一的外壳断点 `767px`**，只管"页面骨架"（导航、容器宽度、弹窗、表单）；
2. 页面内部的**排版细节**继续用各组件已有的 `480/560/700` 规则（它们都在 767 之下，天然叠加生效）。

> 顺序保证：`global.css` 在 `main.js` 里先于组件样式注入，组件 scoped 规则天然后到、优先级更高 → **页面级微调不会被全局规则覆盖**。这也是我坚持把"网格/卡片"类改动写进**组件 scoped**、而不是全塞进 global.css 的原因。

## 五、风险与不做的事

| 风险 | 说明 | 处理 |
|---|---|---|
| PC 端回归 | `AppNav` 模板结构变动 | 所有新样式都关在 `@media (max-width: 767px)` 内；>767px 时 `display: none`，DOM 多几个节点但不参与布局 |
| 底部 Tab 遮挡内容 | 固定定位会盖住页面最后一行 | `.page { padding-bottom: calc(72px + env(safe-area-inset-bottom)) }` |
| iOS 键盘 | `100dvh` 在 iOS 15 以下不认 | `height: calc(100vh - X)` 先写，`100dvh` 后写覆盖；再加 `visualViewport` 监听兜底 |
| 双指缩放误触页面缩放 | 全局未禁 user-scalable（**故意不禁**，无障碍要求） | 只在查看器容器上 `touch-action: none`（已有） |
| autoprefixer | 项目**未安装** autoprefixer，Vite 默认不加前缀 | 改用 `build.target: ['chrome87','safari14','ios14']` + 手写关键 `-webkit-`（代码里已有此惯例），**零新依赖**；如需兼容 iOS 12 再加装 |

**明确不做**：不引入 Vant / 任何移动端 UI 库；不改造 `MerchantLayout`；不做 PWA；不改任何接口与业务逻辑。

## 六、验收标准（自测清单）

| 项 | 通过标准 |
|---|---|
| 375×667（iPhone SE） | 首屏无横向滚动；顶栏仅 Logo + 头像；底栏 4 项可点且高亮正确 |
| 390×844（iPhone 12/13） | 列表 2 列；卡片标题不超 2 行省略 |
| 414×896 / 430×932 | 同上，无元素溢出 |
| 768（iPad 竖屏） | **回到 PC 布局**（7 项顶栏），这是断点边界，必须验 |
| 1280 / 1440 | 与改造前**逐像素一致** |
| 弹窗 | 宽度 ≥90vw 或全屏，内容不横向溢出 |
| 表单 | label 在输入框上方，左对齐 |
| 智能体 | 键盘弹起后输入框仍在可视区 |
| 3D | 单指旋转、双指缩放均生效 |
| 360° | 单指旋转、双指缩放（新增）均生效 |
