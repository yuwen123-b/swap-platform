## 2. 现有 API 封装风格

### 2.1 `src/api/request.js`（唯一 axios 实例，**照抄即可，不改**）

```
baseURL = import.meta.env.VITE_API_BASE_URL || '/api/admin'   // .env 里是 /api/admin
timeout = 15000
```

- **请求拦截**：从 `localStorage.getItem('admin_token')` 取 token → `Authorization: Bearer <token>`
- **响应拦截（成功分支）**：若 body 含 `code` 字段 → **只有 `code === 200` 才 resolve(body)**，否则 `ElMessage.error(body.message)` + `Promise.reject` → **所以页面里拿到的已经是解包后的 `res.data`，且不必自己判 `code`**
- **响应拦截（失败分支）**：`401` → 清 `admin_token`/`admin_info` + 提示「登录已过期」+ `router.push('/login')`；`403` → 提示「无权限执行该操作」；其余 → 提示 `response.data.message`

### 2.2 单文件风格（`api/item.js` 为模板）

```js
import request from './request'
export const getItems = (params) => request.get('/items', { params })
export const auditItem = (id, data) => request.post(`/items/${id}/audit`, data)
```

→ 一行一个具名导出、不写 `async/await`、不写 try/catch、错误提示交给拦截器。**新增 `api/merchant.js` 完全照此风格。**

### 2.3 页面数据流（`ItemAudit.vue` 为模板）

`load()` 里 `try { const res = await xxx(query); list.value = res.data.list; total.value = res.data.total } finally { loading.value = false }` —— 分页响应固定 `{total, page, size, list}`，**7 个商家接口全部同构**，可直接复用。

## 5. 潜在冲突（按严重度排序）

### 🔴 C1（阻断级）结算页的「积分总额 / 佣金」无接口可取，导致二次确认弹窗给不出正确数字

**事实**：
- `GET /merchant/list` 返回 `redemption_count`（`status=2` 的**累计**单数，**无时间范围**）、`commission_rate`，但**不返回积分总额**，也**不返回汇率**
- 汇率 `MERCHANT_POINTS_TO_YUAN=0.01` **只存在于后端 `config.py` / `.env`，没有任何管理端接口暴露它** → 前端**无法**自行算佣金
- 唯一含「积分/佣金」的接口：`/merchant/settlements`（**只有已结算过的**，当前 0 行）、`/merchant/stats`（**全平台合计**，非按商家）
- `settle_merchant` 的真实口径是：**该商家 + 当月 + `redeemed_at` 落在区间 + `status=2`** 的单

**后果**：任务书第 4 条要求弹窗显示「即将结算：N 单核销，¥X 佣金」。用现有数据硬凑，会在两种真实场景下**承诺错误数字**：
1. **跨月**：`redemption_count` 是累计，而结算只吃当月 → N 偏大
2. **本期已结算**：结算幂等（返回原记录不重写），按钮看起来还能点 → 提示「将结算 N 单」实际 0 单

对**不可逆操作**给出错误承诺，是这次最需要避免的风险。

**三个方案（需你选）**：

| 方案 | 做法 | 代价 | 弹窗数字 |
|---|---|---|---|
| **A（推荐）** | 后端 **+1 个只读接口** `GET /api/admin/merchant/settlements/preview?period=YYYY-MM`，按 `settle_merchant` 同一口径返回每个已通过商家的 `{merchant_id, name, redemption_count, points_total, commission_amount, settled, settled_at}`。约 40 行，复用 `parse_period` + `calculate_commission`，零副作用 | 破「后端 0 改动」约束 | ✅ 100% 准确，且能永久禁用本期已结算的行 |
| **B** | 守住 0 改动：结算页只做「历史记录 + 触发结算」，**弹窗不显示 N/¥**，改为「即将为「X 店」结算 2026-10 周期，操作不可撤销」；per-merchant 列表的「核销单数」用累计口径**并如实改列名为「累计核销」** | 不满足任务书第 4 条原文 | ⚠️ 无数字 |
| **C** | 0 改动 + 前端硬编码 `0.01` 估算 | 汇率写死前端（配置漂移）；`积分总额` 仍需逐商家分页拉完所有兑换单求和（N 次请求），且仍非当期口径 | ❌ 会失真，**不推荐** |

### 🔴 C2（阻断级）「停业」按钮无接口，会把商家误标成「已拒绝」

任务书要求「已通过 → [查看详情] [停业]」。但 `PUT /{id}/audit` 只能写 `status=1`（通过）或 `2`（拒绝），**写不出 3（已停业）**；当前也没有 `PUT /merchant/{id}/status` 这类接口。
**若照抄 audit 接口传 `approved:false`，会把「停业」做成「拒绝」**——状态语义错、且商家端会看到 `audit_reason`。
→ **建议本期去掉「停业」按钮**（不改后端）；若必须要有，需在 C1 方案 A 里一并加一个改状态接口（另需确认是否允许改 `commission_rate`）。

### 🟡 C3 兑换订单的「日期范围」筛选后端不支持

`GET /merchant/orders` 只支持 `status / merchant_id / keyword / page / size`，**无起止日期**。
→ 建议本期**不做**日期范围（与前 11 个管理端页面一致：`OrderList.vue` 也只有关键词搜索）。若要做，需随 C1 方案 A 一起加 `start_date/end_date` 参数。

### 🟡 C4（需澄清）权限写法自相矛盾：`meta.roles=[1,2]` 与「role 3 只能看」不能同时成立

任务书写「权限：`meta.roles = [1, 2]`」，又写「审核员 role 3 **只能看**，不能操作」。但守卫是 `if (!to.meta.roles.includes(store.role)) return '/403'` —— 若 `meta.roles=[1,2]`，**role 3 直接被踢到 /403，根本进不了页面**，谈不上「只能看」。
→ **建议**：三条路由 `meta.roles = [1, 2, 3]`（与后端 `read_roles` 完全一致），按钮级用 `store.role !== 3` 控制 [通过]/[拒绝]/[结算] 的 `v-if` 与 `:disabled`。这样 role 3 能进页面看数据、点不到写按钮，**且不会出现「页面进得去、点了 403」**。

### 🟢 C5（坑）审核是 PUT 不是 POST

`POST /api/admin/merchant/{id}/audit` → **405**。正确是 `PUT /api/admin/merchant/{id}/audit`（body `{approved, reason}`）。
`api/item.js` 的 `auditItem` 恰好是 POST，直接照抄会踩坑。

### 🟢 C6（坑）`triggerSettle()` 是全量结算，不可逆且影响 5 家商家

任务书 API 清单里有 `triggerSettle()`（`POST /merchant/settle`，无参数 = **结算全部已通过商家**）。
→ 建议**封装进 api 文件但不挂到主 UI**（或仅超管可见、需输入「结算」二字确认）。按行结算 `triggerSettleOne(id)` 足够覆盖任务书第 4 条。

### 🟢 C7 词汇撞车：两个「订单」

既有菜单「订单管理」= **物品交换单**（`/orders`）；新增「兑换订单」= **商家兑换单**（`/merchant/orders`）。两者数据源、状态枚举、表结构完全不同（`status` 1待核销/2已核销/3已过期/4已取消 vs 交换单体系）。
→ 菜单标题与页面标题都统一用「**兑换**」二字区分，避免运营误操作。

### 🟢 C8 `logo_url` 是签名 URL，不要回写

`to_merchant_info` 里 `logo_url = sign_relative(...)`（带 `exp`/`sig` 的**签名 URL**）。本模块只读展示，**不要**把它当原值回填到任何表单/更新请求（阶段三已在商家端踩过这个坑）。

## 6. 后端 7 接口逐条比对（已实测全部可用，`code:200`）

| 接口 | 方法 | 参数 | 返回关键字段 | 本模块用途 |

| `/merchant/settle` | POST | body `{merchant_id?, period?}` | `period,count,commission_total,list[]` | 全量结算（见 C6） |
| `/merchant/settle/{id}` | POST | body `{period?}` | 单个结算结果（含 `already_settled` 标记） | 按行结算 ✅ |

**结论**：3 条主链路（审核 / 看订单 / 看结算记录）**完全够用**；缺的恰好是 C1 的「按商家、按当期的待结算积分与佣金」。
